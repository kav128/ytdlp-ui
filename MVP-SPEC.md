# ТЗ: MVP WebUI для yt-dlp

Дата: 2026-10-01. Документ фиксирует требования, согласованные при обсуждении MVP.

Предлагаемые технические решения и открытые вопросы описаны в [TECHNICAL-DESIGN.md](TECHNICAL-DESIGN.md).

Текущий этап реализации: каркас и интерфейс библиотеки с моковым бэкендом, по указанию пользователя. Демонстрационные данные и сессии хранятся в памяти и сбрасываются при перезапуске; реальные загрузки и хранилища на этом этапе не подключены. Это промежуточный этап, а требования к итоговому MVP ниже сохраняются.

## 1. Назначение

Веб-приложение для постановки заданий на скачивание, управления загрузками и публичного доступа к файлам в S3.

## 2. Стек и сборка

- ASP.NET Core 10.0 Web API и React в одном проекте.
- HTTP API реализуется через ASP.NET Core Minimal API вместо контроллеров.
- API и фронтенд раздаются через Kestrel.
- Фронтенд автоматически собирается при `dotnet build` и `dotnet publish`.
- Docker-native приложение, multi-stage сборка образа.
- Поддерживаемые платформы приложения и всех runtime-зависимостей — `linux/amd64` и `linux/arm64`.
- SQLite через Entity Framework Core для хранения заданий, этапов и истории попыток.
- База данных и временные файлы сохраняются в Docker volumes.

## 3. Доступ

Без авторизации доступны каталог файлов и скачивание на устройство.

Для администратора доступны создание заданий, просмотр статусов и истории, повтор, отмена и удаление файлов из библиотеки.

Вход выполняется через всплывающую форму в правом верхнем углу. После авторизации та же страница библиотеки получает функции управления: блок заданий, создание загрузки и удаление файлов. В MVP используется один администратор с учетными данными в конфигурации бэкенда.

Вход рассчитан на текущую сессию вкладки браузера через `sessionStorage`, без функции «Запомнить меня». Перезагрузка страницы сохраняет токен; при запуске UI проверяет действительность сессии на бэкенде. Для администратора доступна кнопка выхода. После выхода токен и административные данные удаляются из клиентского состояния, а доступ к защищенным API требует нового входа. Выход не отменяет фоновые задания.

Аутентификация административных запросов реализуется через JWT в заголовке `Authorization: Bearer <token>`; права администратора проверяются бэкендом. JWT хранится на клиенте в `sessionStorage` и очищается при выходе или подтвержденном истечении/отзыве сессии. Срок действия и механизм выхода описываются в техническом проекте.

## 4. Создание загрузки

Единственный вводимый параметр — URL источника.

Дубликаты определяются по URL, без распознавания одного ролика по разным ссылкам. Создание нового задания с уже зарегистрированным URL отклоняется с понятным сообщением, кроме случая, когда ранее скачанный файл удален: повторная отправка этого URL запускает новую попытку старого задания. Новая логическая загрузка при этом не создается, история сохраняется.

Действие «Повторить» у существующего задания также создает новую попытку той же загрузки. После удаления готового файла оно запускает скачивание заново. Проверка доступности S3, завершившаяся сетевой ошибкой или отказом доступа, не считается подтверждением удаления файла.

Поддерживаются отдельные ролики с публичных источников, поддерживаемых yt-dlp. Плейлисты и прямые эфиры отклоняются.

Скачивается видео с аудио до 1080p, с предпочтением MP4. Если подходящий вариант доступен в другом формате, он сохраняется без перекодирования. При необходимости отдельные дорожки объединяются без перекодирования.

## 5. Очередь и этапы

Одновременно выполняется одно задание. Остальные ожидают в очереди.

Этапы обработки:

1. Скачивание во временное локальное хранилище.
2. Объединение аудио и видео при необходимости.
3. Отправка готового файла в S3.
4. Удаление локальных файлов после успешной отправки.

Задание считается завершенным после успешного сохранения результата в S3 и очистки локальных файлов. Опубликованный файл доступен в библиотеке уже после подтверждения отправки в S3, даже если локальная очистка еще выполняется или завершилась ошибкой. Дополнительные ограничения размера файла и длительности ролика в MVP не вводятся.

## 6. Статусы и восстановление

Интерфейс показывает состояние задания, текущий этап и сведения об ошибке.

Жизненный цикл задания моделируется конечным автоматом с явно определенными событиями, допустимыми переходами и условиями их выполнения. Этапы обработки являются состояниями автомата: в очереди → скачивается → подготавливается/объединяется → отправляется в S3 → удаляются локальные файлы → завершено. По команде удаления готового результата: завершено → удаляется из S3 → удалено. Объединение выполняется только при необходимости. Дополнительные состояния — ошибка, отменяется и отменено. Доступность опубликованного файла учитывается отдельно как факт о хранилище и не заменяет состояния автомата.

Состояния этапов и история попыток хранятся в БД. При отказе сохраняются состояние, на котором произошла ошибка, и точка продолжения. После перезапуска прерванное задание помечается ошибкой и требует ручного повтора, включая очистку и удаление из S3. Ожидающие задания сохраняются в очереди. Повтор возобновляет нужный этап после проверки фактического результата прерванной операции.

## 7. Повтор и отмена

При ошибке промежуточные файлы сохраняются без автоматического удаления по сроку.

В карточке задания доступны действия:

- **«Повторить»** — создает новую попытку в истории той же загрузки, повторяет проваленный этап и продолжает последующие. Результаты успешно выполненных этапов используются повторно.
- **«Отменить и удалить файлы»** — останавливает обработку и удаляет промежуточные результаты задания. Запись в истории сохраняется.

В состоянии `CleaningUp` отмена запрещена. Запрет сохраняется после ошибки этого этапа и при ожидании его повтора: доступен повтор очистки, а не отмена с удалением опубликованного результата. UI не предлагает отмену, бэкенд отклоняет такую команду. После завершения очистки готовый файл можно удалить через библиотеку.

Например, после ошибки отправки в S3 повторно отправляется уже подготовленный файл без нового скачивания источника.

После ошибки локальной очистки повторяется только очистка, а после ошибки удаления из S3 — только удаление. Уже успешно выполненные действия не повторяются, если их результат подтвержден. Возобновление означает продолжение с этапа, а не обязательную докачку с точностью до байта.

После удаления готового файла повтор начинает скачивание с начала в рамках того же задания. Повторная отправка его URL через форму создания вызывает тот же механизм. Обычный публичный запрос скачивания отсутствующего файла возвращает ошибку отсутствия; запуск заданий остается административным действием.

## 8. S3 и публичная библиотека

Используется MinIO через официальный пакет `AWSSDK.S3`. Параметры подключения и учетные данные задаются конфигурацией.

Bucket общедоступен на чтение; запись и удаление требуют авторизации.

Каталог показывает все файлы bucket, включая добавленные вне приложения. Представление — плоский список без навигации по папкам, с названием, размером, датой изменения и действием скачивания.

В MVP каталог небольшой и отображается целиком, без пользовательской пагинации или кнопки «Показать еще». При получении списка из S3 бэкенд должен собрать все страницы ответа хранилища, чтобы не обрезать каталог.

Скачивание посетителем проксируется через бэкенд приложения.

Администратор может удалить файл из S3; после удаления он исчезает из каталога.

Если удаленный файл был создан приложением, связанное задание переходит в состояние «Удалено», его история остается в БД с возможностью повторного скачивания. При удалении вне приложения переход выполняется после подтверждения отсутствия объекта в S3. Для файлов, добавленных вне приложения, наличие задания в БД не требуется.

## 9. Интерфейс и локализация

### Визуальный стиль

- Визуальный ориентир — Google Material 3, Material You и Material 3 Expressive.
- Плотность интерфейса — средняя между компактной и просторной; действия располагаются в правом нижнем углу карточек.
- Интерфейс адаптируется под телефон и десктоп, включая административные действия.
- Светлая или темная тема выбирается автоматически по настройкам устройства. Ручной переключатель темы в MVP не требуется.

### Единая страница библиотеки

- Посетитель без входа видит каталог готовых файлов и может скачать файл на свое устройство.
- Каталог готовых файлов выводится целиком, без порционной загрузки в интерфейсе.
- После входа доступна кнопка выхода из административной сессии.
- После входа администратора над каталогом появляется отдельный блок «Загрузки» с очередью и историей заданий. Этот блок и его данные доступны только администратору.
- В блоке загрузок находится кнопка создания задания. Поле URL и действие отправки задания открываются по нажатию этой кнопки; постоянно открытая форма не нужна.
- В том же каталоге готовых файлов администратору становится доступно удаление. Отдельная страница или вкладка управления библиотекой в MVP не требуется.
- Поиска по файлам в MVP нет.

### Карточка задания

- Показывает название ролика, а пока оно неизвестно — URL, текущий этап, прогресс, дату создания и доступные действия.
- Показывает сведения об ошибке, если попытка завершилась неудачно.
- Если для текущего этапа доступен процент прогресса, отображает его с индикатором выполнения. Когда точный процент недоступен, показывает этап и индикатор без процента; выдуманный процент или оценка общего прогресса не используются.
- Кнопки действий располагаются справа внизу карточки и соответствуют состоянию задания, включая повтор и отмену с удалением промежуточных файлов.
- Скорость скачивания и оставшееся время не требуются в MVP.

### Локализация

- Поддерживаются английский и русский языки. Английский — базовый и запасной язык.
- Язык определяется по языковым предпочтениям браузера. Ручной переключатель языка в MVP не требуется.
- Все пользовательские строки интерфейса, включая подписи, состояния, формы и сообщения валидации, хранятся в ресурсах локализации.
- Даты и числа форматируются с учетом выбранного языка. Технические сообщения сторонних инструментов могут показываться как диагностические подробности без перевода.

## 10. Развертывание

Основной сценарий — запуск контейнера приложения с подключением к существующему MinIO.

Для `linux/amd64` и `linux/arm64` публикуется один тег multi-platform образа в GHCR с общим manifest list. Обе платформы должны обеспечивать весь функционал MVP. Базовые образы, .NET runtime, нативные зависимости SQLite, yt-dlp и FFmpeg должны соответствовать целевой архитектуре.

Дополнительно предоставляется Compose для локального запуска приложения вместе с MinIO.

## 11. Структура репозитория и общие настройки

Планируемая структура:

```text
/
├── readme.md
├── MVP-SPEC.md
├── AGENTS.md
├── Ytdlp.Ui.slnx
├── global.json
├── Directory.Build.props
├── Directory.Packages.props
├── Dockerfile
├── .dockerignore
├── compose.yaml
├── .github/
│   └── workflows/
│       └── ci.yml
├── src/
│   ├── Directory.Build.props
│   └── Ytdlp.Ui/
│       ├── Ytdlp.Ui.csproj
│       └── ClientApp/
└── tests/
    ├── Directory.Build.props
    └── Ytdlp.Ui.Tests/
        └── Ytdlp.Ui.Tests.csproj
```

Это целевая структура для реализации; наличие элементов в схеме не означает, что они уже созданы. Дополнительные тестовые проекты допускаются по мере необходимости.

### Решение и приложение

- В корне находится решение в формате `.slnx`, включающее production- и тестовые проекты.
- Production-код размещается в `src/`, тестовые проекты — в `tests/`.
- ASP.NET Core и React остаются в одном проекте приложения: исходники React находятся в `ClientApp/` внутри веб-проекта. Тестовые проекты создаются отдельно.

### Общие настройки сборки

- `global.json` фиксирует версию .NET SDK и политику ее выбора. Конкретная версия SDK определяется при создании каркаса и согласуется с CI и Docker-сборкой.
- Корневой `Directory.Build.props` задает общие свойства: `TargetFramework=net10.0`, `LangVersion`, `Nullable=enable`, `ImplicitUsings` и другие согласованные настройки сборки. Не используются плавающие `latest` или `preview` для версии языка.
- Тип SDK проекта задается в `.csproj`: для приложения — `Microsoft.NET.Sdk.Web`, для тестов — `Microsoft.NET.Sdk`.
- `src/Directory.Build.props` и `tests/Directory.Build.props` содержат настройки своей группы проектов и явно импортируют корневой файл перед собственными настройками.
- Дополнительные `Directory.Build.props` внутри отдельных проектов допустимы при необходимости; они также явно импортируют настройки родительского уровня.
- Доступ тестов к внутренним типам через `InternalsVisibleTo` настраивается со стороны production-проектов, при необходимости централизованно в `src/Directory.Build.props`, для конкретных тестовых сборок.
- Общие тестовые настройки и ссылки на NUnit, NSubstitute, тестовый SDK и адаптер размещаются в `tests/Directory.Build.props`. Тестовые зависимости не добавляются production-проектам.
- Для интеграционных тестов используется Testcontainers for .NET: тесты самостоятельно запускают изолированный MinIO и освобождают его ресурсы. Доступ к существующему пользовательскому MinIO для тестов не требуется. SQLite проверяется на настоящей файловой БД во временном каталоге.
- Контейнерные интеграционные тесты требуют доступного Docker и выполняются в CI перед публикацией образа. Unit-тесты запускаются без Docker. Требования к окружению и команды отдельных наборов тестов документируются в `readme.md` при реализации.

### Централизованное управление пакетами

- В корне находится `Directory.Packages.props` с включенным Central Package Management (`ManagePackageVersionsCentrally=true`).
- Версии NuGet-пакетов задаются в нем через `PackageVersion`.
- Ссылки `PackageReference` в проектах и общих props-файлах не содержат собственных версий.
- CPM относится к NuGet; зависимости React управляются через `package.json` и lock-файл внутри `ClientApp/`.

### Документация

Корневой `readme.md` содержит:

- Краткое описание функционала и границ MVP.
- Схему API: методы и маршруты, назначение, требования авторизации, основные запросы, ответы и ошибки.
- Требования к окружению, порядок восстановления зависимостей, сборки, публикации и запуска тестов.
- Порядок сборки Docker-образа и развертывания с существующим MinIO, параметры конфигурации и volumes.
- Вспомогательный сценарий запуска через Compose.

Команды и схема API в `readme.md` должны соответствовать фактической реализации. `MVP-SPEC.md` хранит требования, а `AGENTS.md` — инструкции по работе с кодом и документацией.

### GitHub Actions

- Workflow располагается в `.github/workflows/ci.yml` и запускается для push в основную ветку и pull request в нее. Имя основной ветки берется из настроек фактического репозитория.
- За основу берется [workflow ResultService](https://github.com/Texnokaktus-ProgOlymp/ResultService/blob/master/.github/workflows/dotnet.yml), адаптированный под структуру и зависимости этого проекта.
- Job `build` восстанавливает зависимости, собирает решение вместе с React, запускает тесты и проверяет публикацию приложения через `dotnet publish`.
- Job `docker` зависит от успешной `build` через `needs: build` и собирает образ из корневого multi-stage `Dockerfile` с помощью Docker Buildx.
- Docker-сборка выполняется для `platforms: linux/amd64,linux/arm64`. Для выполнения команд целевой архитектуры используются соответствующие runners или QEMU.
- CI собирает образы для обеих платформ без запуска приложения или smoke-тестов образов. Проверки запуска API, React, SQLite, yt-dlp и FFmpeg выполняются отдельно в подходящем окружении; успешная сборка образа сама по себе не подтверждает работоспособность.
- При push в основную ветку job `docker` публикует образ в GitHub Container Registry (GHCR). Для pull request выполняется проверка сборки образа без входа в реестр и без публикации.
- Имя образа — `ghcr.io/<repository-owner>/ytdlp-ui`, в нижнем регистре; владелец определяется из контекста GitHub Actions.
- Для входа в GHCR используются `github.actor` и `GITHUB_TOKEN`. Job публикации получает `contents: read` и `packages: write`; job проверок достаточно `contents: read`.
- Тег образа формируется по примеру: `YYYY.M.D.<github.run_number>`. Дата берется из коммита в часовом поясе `Europe/Moscow`; теги и OCI labels передаются сборке через Docker metadata action.
- Версия .NET SDK в CI берется из `global.json`; окружение сборки фронтенда согласуется с Docker-сборкой.
- Из примера используются разделение jobs, зависимость публикации от проверок, вход в GHCR, Buildx и подготовка метаданных образа. Настройка стороннего приватного NuGet feed, передача токена внутрь Docker-сборки и создание Git-тегов не требуются для текущего проекта.
- Автоматический деплой приложения не входит в текущие требования к pipeline. Порядок получения образа из GHCR и его запуска описывается в `readme.md`.

Справочные материалы: [настройки MSBuild по каталогам](https://learn.microsoft.com/en-us/visualstudio/msbuild/customize-by-directory), [выбор .NET SDK через global.json](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json), [NuGet Central Package Management](https://learn.microsoft.com/en-us/nuget/consume-packages/central-package-management).

## 12. После MVP

Отдельно прорабатываются:

- Запись прямых эфиров.
- Выбор формата.
- Перекодирование.
- Телеметрия скачивания файлов через бэкенд.

Вопрос для будущей оценки: целесообразность запуска yt-dlp в отдельном контейнере с использованием готового образа. Это идея для обсуждения после MVP, а не принятое решение об изменении архитектуры.
