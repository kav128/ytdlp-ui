# Спецификации yt-dlp WebUI

Согласованные требования MVP перенесены из `MVP-SPEC.md` в основные спецификации OpenSpec 2026-11-03. Исходное ТЗ
датировано 2026-10-01 и содержит последующие согласованные изменения. Миграция меняет форму хранения документации,
сохраняя требования и границы MVP.

## Назначение и источники

Веб-приложение ставит задания на скачивание отдельных роликов, управляет загрузками и предоставляет публичный доступ к
файлам S3. Используется схема OpenSpec `spec-driven`.

| Источник                     | Назначение                                                                                      |
|------------------------------|-------------------------------------------------------------------------------------------------|
| [specs/](specs/)             | Согласованный контракт целевого MVP с требованиями и сценариями                                 |
| [design.md](design.md)       | Общий технический проект, статус реализации, варианты решений, план проверок и открытые вопросы |
| [config.yaml](config.yaml)   | Контекст и правила подготовки новых артефактов OpenSpec                                         |
| [changes/](changes/)         | Будущие изменения требований, design и задачи конкретных изменений                              |
| [../AGENTS.md](../AGENTS.md) | Инструкции работы над проектом                                                                  |
| [../readme.md](../readme.md) | Фактический функционал, API, команды, конфигурация и развертывание                              |

Основные спеки описывают целевой MVP. Они не являются отчетом о готовности и
не заменяют проверку реализации. При миграции не создавались фиктивные завершенные changes или задачи реализации.

## Состояние реализации

Реализованы ASP.NET Core/React MVP, агрегат `Download`, постоянные API/очередь и схема PostgreSQL. Миграции
применяются до приема запросов, а недоступная БД прерывает startup без локального fallback. PostgreSQL начинается
с чистой БД по [последующему решению](changes/postgresql-persistence/proposal.md), без импорта SQLite и прежних tickets.
Авторизация переведена на Authentik OIDC с проверкой группы, серверной HttpOnly cookie и ticket PostgreSQL на 12 часов без
sliding; ключи Data Protection и отзыв сохраняются при перезапуске. Контракт доступа
задается [administrator-access](specs/administrator-access/spec.md); согласованные delta включены в основную спеку.

Каталог читает все страницы S3, включая внешние объекты; произвольные файлы отправляются администратором и скачиваются
публично потоком. Безопасное удаление сохраняет историю связанных публикаций. Очередь и intent сохраняются при
перезапуске. Настоящий worker последовательно выполняет yt-dlp, подготовку copy через FFmpeg/FFprobe, подтвержденную
публикацию и очистку; план/артефакты/прогресс сохраняются в PostgreSQL. Startup recovery помечает прерванные операции
для ручного повтора; проверка файлов и S3 согласует результаты до повторных действий. Own DELETE202 использует общую очередь.
UI показывает живую историю попыток/этапов, локализованные причины и reuse, обновляет публичный каталог и учитывает
актуальные allowedActions. Production Dockerfile содержит готовые инструменты обеих архитектур; отдельные запуски
AMD64 и ARM64 под QEMU подтверждены. Подробности и ограничения проверок сохранены в [плане этапов](implementation-plan.md),
[журнале ревью](review-log.md), `design.md` и корневом `readme.md`; наличие спеки само по себе не подтверждает реализацию.

## Границы MVP

В MVP отсутствуют плейлисты, прямые эфиры, выбор формата пользователем, перекодирование, телеметрия скачивания через
бэкенд, поиск по файлам, навигация по папкам и пользовательская пагинация каталога. Нет ручного переключения языка/темы,
отдельной административной страницы, отдельных сервисов очередей или нескольких БД, автоматического удаления временных файлов по
сроку или ограничений размера и длительности ролика.

Прямые эфиры, выбор формата, перекодирование и телеметрия требуют отдельной итерации. Возможность запуска yt-dlp в
отдельном контейнере — идея для оценки после MVP; для MVP сохраняется дочерний процесс внутри контейнера приложения.

Предложенные polling, порядок сортировки, формат S3-ключей и другие технические defaults находятся в `design.md`. Они не
становятся новыми пользовательскими требованиями из-за миграции. Согласованные решения отмечены в его разделе 15.

## Работа с OpenSpec

Из корня репозитория:

```powershell
openspec list --specs
openspec show download-lifecycle --type spec
openspec validate --all --strict --no-interactive
```

Новые изменения оформляются в `changes/` через существующие OpenSpec workflows; технический проект конкретного изменения
хранится в его `design.md`. Общие требования обновляются вместе с согласованным изменением. Миграция не создает список
задач оставшейся реализации и не запускает ее автоматически.
