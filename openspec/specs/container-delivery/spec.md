# Контейнер, конфигурация и поставка

## Purpose

Определяет сохраняемое развертывание с MinIO, поддержку двух архитектур и проверку, сборку и публикацию контейнерного образа в GHCR.

## Requirements

### Requirement: Контейнер приложения и существующий MinIO

Проект ДОЛЖЕН (SHALL) предоставлять multi-stage Dockerfile одного приложения с .NET runtime, готовым React, yt-dlp и средствами объединения дорожек. Основной сценарий — отдельный контейнер с существующим MinIO; Compose с MinIO служит вспомогательным локальным вариантом.

#### Scenario: Основное развертывание
- **WHEN** оператор запускает контейнер с настройками существующего MinIO
- **THEN** приложение использует этот MinIO без обязательного запуска нового сервиса хранилища

#### Scenario: Локальный Compose
- **WHEN** оператор использует вспомогательный Compose
- **THEN** приложение может запускаться вместе с локальным MinIO

### Requirement: Сохраняемая конфигурация и данные

Приложение ДОЛЖНО (SHALL) хранить SQLite и временные файлы в сохраняемых volumes. Параметры MinIO, учетные данные и пути хранения задаются конфигурацией с переопределением переменными окружения; команды запуска и подключаемые volumes описываются в `readme.md`.

#### Scenario: Замена контейнера
- **WHEN** контейнер заменяется с подключением прежних volumes
- **THEN** БД, очередь, история и промежуточные файлы сохраняются для правил восстановления

#### Scenario: Настройки окружения
- **WHEN** оператор переопределяет параметры подключения или пути переменными окружения
- **THEN** приложение использует заданные настройки без пересборки фронтенда

### Requirement: Полный функционал двух архитектур

Приложение ДОЛЖНО (SHALL) обеспечивать полный MVP на `linux/amd64` и `linux/arm64`. Базовые образы, .NET, нативные зависимости SQLite, yt-dlp и FFmpeg должны соответствовать целевой архитектуре; один тег в GHCR содержит общий manifest list обеих платформ.

#### Scenario: Сборка целевых платформ
- **WHEN** Buildx собирает образ для AMD64 и ARM64
- **THEN** каждая платформа получает совместимые runtime-зависимости без копирования чужих нативных бинарных файлов
- **AND** команды целевой архитектуры выполняются подходящим runner или QEMU

#### Scenario: Получение опубликованного тега
- **WHEN** оператор получает один опубликованный тег на AMD64 или ARM64
- **THEN** manifest list выбирает образ соответствующей платформы

### Requirement: Проверки перед упаковкой

Workflow `.github/workflows/ci.yml` ДОЛЖЕН (SHALL) запускаться на push в основную ветку и pull request в нее. Job `build` отдельно собирает React и .NET, выполняет тесты и проверяет publish с готовым UI; job `docker` запускается с `needs: build`.

#### Scenario: Успешная проверка
- **WHEN** job `build` успешно завершила сборку, тесты и проверку публикации
- **THEN** job `docker` может собирать образ из корневого Dockerfile через Buildx

#### Scenario: Ошибка проверки
- **WHEN** сборка, обязательный тест или publish завершились ошибкой
- **THEN** зависимая публикация образа не выполняется

### Requirement: CI не запускает приложение и образы

CI ДОЛЖЕН (SHALL) собирать `platforms: linux/amd64,linux/arm64` без запуска приложения и smoke-тестов готовых образов. Работоспособность API, React, SQLite, yt-dlp и FFmpeg на обеих платформах проверяется отдельно в подходящей среде; сборка не заменяет проверку запуска.

#### Scenario: Проверка pipeline
- **WHEN** выполняется CI
- **THEN** он собирает обе платформы, но не запускает приложение или smoke-тесты образов
- **AND** контейнерные тесты зависимостей через Testcontainers остаются обязательными

#### Scenario: Платформа недоступна локально
- **WHEN** отдельный запуск одной из архитектур проверить невозможно
- **THEN** это ограничение явно указывается без заявления о работоспособности по результату одной сборки

### Requirement: Публикация GHCR только из основной ветки

Job публикации ДОЛЖЕН (SHALL) на push в основную ветку публиковать `ghcr.io/<repository-owner>/ytdlp-ui` в нижнем регистре. Для pull request выполняются проверки и сборка без входа в GHCR и без публикации; автоматический деплой в pipeline не входит.

#### Scenario: Push в основную ветку
- **WHEN** проверки и сборка обеих платформ успешны для push в фактическую основную ветку
- **THEN** образ публикуется в GHCR с общим manifest list

#### Scenario: Pull request
- **WHEN** workflow запущен для pull request в основную ветку
- **THEN** образ только собирается без входа в реестр и публикации

### Requirement: Полномочия и учетные данные CI

Workflow ДОЛЖЕН (SHALL) использовать `github.actor` и `GITHUB_TOKEN` для GHCR, `contents: read` для репозитория и `packages: write` только для job публикации. Приватные NuGet feeds, секреты Docker-сборки и создание Git-тегов не добавляются без отдельной необходимости.

#### Scenario: Доступ jobs
- **WHEN** выполняются проверка и публикация
- **THEN** job проверок имеет чтение репозитория, а право записи пакетов принадлежит только job публикации
- **AND** для входа не требуется отдельный пользовательский токен

### Requirement: Календарный тег и метаданные

Workflow ДОЛЖЕН (SHALL) формировать тег `YYYY.M.D.<github.run_number>` по дате коммита в `Europe/Moscow`, передавать теги и OCI labels через Docker metadata action и согласовывать SDK с `global.json`, CI и Docker.

#### Scenario: Коммит около смены дня
- **WHEN** дата коммита в исходном часовом поясе отличается от календарной даты в Москве
- **THEN** календарная часть тега использует дату `Europe/Moscow`
- **AND** номер запуска берется из `github.run_number`
