# Структура, сборка и проверки приложения

## Purpose

Определяет контракт структуры репозитория, независимой сборки React и .NET, состава публикации и обязательных проверок перед поставкой MVP.

## Requirements

### Requirement: Одно приложение и корневое решение

Репозиторий ДОЛЖЕН (SHALL) содержать корневое решение `Ytdlp.Ui.slnx` со всеми production- и тестовыми проектами. Бэкенд ASP.NET Core 10 Web API находится в `src/Ytdlp.Ui/`, React — в `src/Ytdlp.Ui.Client/`, отдельные тестовые проекты — в `tests/`; Kestrel раздает API и собранный UI одного приложения.

#### Scenario: Новый проект решения

- **WHEN** добавляется production- или тестовый проект
- **THEN** он размещается в соответствующем каталоге и включается в корневое `.slnx`

#### Scenario: Публикация приложения

- **WHEN** приложение развернуто
- **THEN** один Web-проект и один контейнер обслуживают API и готовый React без отдельного production-сервера фронтенда

### Requirement: Фиксированные общие настройки .NET

Репозиторий ДОЛЖЕН (SHALL) фиксировать SDK в `global.json` согласованно с CI и Docker. Корневой `Directory.Build.props` задает `net10.0`, явный `LangVersion` без `latest`/`preview`, nullable и implicit usings; тип SDK задается в `.csproj`.

#### Scenario: Сборка в разных окружениях

- **WHEN** решение собирается локально, в CI или Docker
- **THEN** используется согласованный SDK и общие настройки компиляции

### Requirement: Наследование production- и тестовых настроек

Репозиторий ДОЛЖЕН (SHALL) разделять настройки в `src/Directory.Build.props` и `tests/Directory.Build.props`, явно импортируя родительский файл до своих настроек на каждом вложенном уровне. Общие зависимости NUnit, NSubstitute, тестового SDK и адаптера принадлежат только тестовым проектам.

#### Scenario: Вложенные настройки

- **WHEN** проект использует групповой или собственный `Directory.Build.props`
- **THEN** сохраняется явная цепочка импорта родительских настроек

#### Scenario: Доступ к внутренним типам

- **WHEN** тестам нужен `InternalsVisibleTo`
- **THEN** доступ задается со стороны production для конкретных нужных тестовых сборок
- **AND** тестовые пакеты не добавляются в production

### Requirement: Централизованные зависимости

Репозиторий ДОЛЖЕН (SHALL) включать CPM через `ManagePackageVersionsCentrally=true` и хранить все версии NuGet в корневом `Directory.Packages.props` как `PackageVersion`, без версий в `PackageReference`. Зависимости React ведутся отдельно в `package.json` и lock-файле клиента.

#### Scenario: Добавление зависимости

- **WHEN** добавляется NuGet-пакет или зависимость React
- **THEN** ее версия фиксируется в соответствующем централизованном файле .NET или файлах клиента
- **AND** Testcontainers подключается только к нужным тестовым проектам

### Requirement: Независимая и явно совместная сборка

Сборка ДОЛЖНА (SHALL) по умолчанию выполнять React и .NET отдельно, включая CI и Dockerfile. Совместная сборка включается только `-p:BuildFrontend=true` или target `BuildFrontend`; готовый UI из `src/Ytdlp.Ui.Client/dist/` включается в `wwwroot` результатов .NET build и publish.

#### Scenario: Обычная сборка .NET

- **WHEN** выполняется `dotnet build` без флага совместной сборки
- **THEN** .NET не запускает npm и допускает сборку API без готового UI

#### Scenario: Явная сборка фронтенда

- **WHEN** указан `-p:BuildFrontend=true` или вызван target `BuildFrontend`
- **THEN** выполняется сборка React в `dist/`
- **AND** результат сборки React не коммитится

#### Scenario: Публикация готового UI

- **WHEN** React предварительно собран и выполняется .NET publish
- **THEN** публикация содержит готовый UI в `wwwroot`

#### Scenario: Публикация без UI

- **WHEN** выполняется publish без готового `dist/index.html`
- **THEN** команда завершается понятной ошибкой о необходимости предварительной сборки React

### Requirement: Изолированные проверки хранилищ

Тесты ДОЛЖНЫ (SHALL) проверять PostgreSQL и MinIO через Testcontainers for .NET с изолированными данными, динамическими портами, ожиданием готовности и освобождением ресурсов; PostgreSQL использует настоящие миграции приложения. Пользовательские PostgreSQL и MinIO не используются.

#### Scenario: Проверка сохранения данных

- **WHEN** запускаются проверки сохранения состояния
- **THEN** используется настоящая PostgreSQL с миграциями вместо SQLite или EF InMemory

#### Scenario: Контейнерная интеграция

- **WHEN** запускаются проверки PostgreSQL или MinIO
- **THEN** тестовая инфраструктура управляет собственным контейнером и изолированными данными
- **AND** ресурсы освобождаются после проверок

### Requirement: Отдельные unit-тесты и обязательный Docker в CI

Проект ДОЛЖЕН (SHALL) поддерживать запуск unit-тестов без Docker и запуск контейнерных интеграционных тестов в CI до публикации образа. Отсутствие Docker в CI не должно приводить к незаметному пропуску; невыполненные локальные проверки сообщаются явно.

#### Scenario: Среда без Docker

- **WHEN** локально Docker недоступен
- **THEN** unit-тесты можно выполнить отдельно
- **AND** контейнерные интеграционные тесты не объявляются успешно выполненными

#### Scenario: Docker отсутствует в CI

- **WHEN** обязательные контейнерные тесты не могут запуститься из-за отсутствия Docker
- **THEN** проверка считается неуспешной, а образ не публикуется

### Requirement: Документация соответствует реализации

Проект ДОЛЖЕН (SHALL) хранить требования в `openspec/specs/`, технический проект в `openspec/design.md`, инструкции в `AGENTS.md`, руководство в корневом `readme.md`. Руководство описывает фактический функционал, API, ошибки, авторизацию, сборку, тесты, конфигурацию и деплой без выдачи планов за проверенные команды.

#### Scenario: Изменение контракта или команд

- **WHEN** меняются API, сборка, тестирование или развертывание
- **THEN** соответствующие разделы `readme.md` обновляются вместе с изменением
- **AND** требования и статус реализации различаются явно

### Requirement: Постоянное хранилище PostgreSQL

Приложение ДОЛЖНО (SHALL) хранить задания, попытки, этапы, артефакты, сведения о публикациях и серверные сессии в PostgreSQL. Изменения схемы оформляются миграциями. Переход с SQLite начинается с чистой БД без импорта прежних данных.

#### Scenario: Первый запуск на PostgreSQL

- **WHEN** приложение запускается с настройками новой PostgreSQL
- **THEN** применяются миграции и используется новая БД без чтения или изменения прежнего SQLite-файла
- **AND** прежние серверные сессии не дают доступа в новой БД

#### Scenario: Недоступная база

- **WHEN** PostgreSQL недоступна либо миграции не могут быть применены
- **THEN** приложение не объявляет успешную готовность и не переходит к SQLite или памяти как запасному хранилищу
