# Журнал ревью MVP

Ревьюер проверяет каждый этап независимо от разработчика. Руководитель принимает решения по разногласиям и разрешает
этапный коммит после проверки исправлений.

## Порядок учета замечаний

- Замечания получают сквозные идентификаторы `R1`, `R2` и далее, приоритет, область этапа, файл и воспроизводимое
  доказательство.
- Для каждого замечания фиксируются требуемое поведение, ответ разработчика, решение руководителя и статус `open`,
  `fixed` или `accepted`.
- `fixed` означает, что исправление перепроверено ревьюером; `accepted` означает, что руководитель принял доказанный
  контраргумент или явно согласовал исключение.
- Проверки, выполненные разработчиком, и независимо выполненные проверки ревьюера указываются раздельно. Сборка не
  считается проверкой запуска.
- Исходные пробелы последующих этапов не являются блокерами текущего этапа только из-за их наличия до его начала.

## Этап 1. Структура репозитория и тестовая инфраструктура

Статус: этап принят после исправления R1/R2 и независимой перепроверки; итоговый журнал ожидает обязательного Reformat
перед коммитом.

### Критерии приемки

- Настройки solution, props и CPM соответствуют `dotnet-repository-structure`: каждый проект включен в solution,
  Solution Items указывают на существующие файлы, вложенные props импортируют родительские; тестовые пакеты не попадают
  в production.
- `.Tests` содержит модульные сценарии; HTTP-pipeline, хост и настоящая файловая SQLite с миграциями проверяются в
  `.IntegrationTests`.
- `CustomWebApplicationFactory` находится в `Tools`, `SetupBase` и `SetupGlobal` — в отдельных файлах корня
  интеграционного проекта; настройка хоста, сценарии и владение ресурсами разделены по `dotnet-integration-tests`.
- Сценарии не зависят от порядка запуска, очистка выполняется после падения assertions, scoped-сервисы не живут весь
  набор; общие изменяемые ресурсы исключают параллельный запуск без изоляции.
- Сохраняются значимые сценарии старого набора, включая миграции, перезапуск, гонки refresh и запрет отмены очистки. На
  этом этапе контракт авторизации и мокового API не меняется.
- SDK закреплен согласованно в `global.json`, Docker и документации; CI выполняет оба тестовых проекта и проверяет
  публикацию с готовым React.
- Приватные поля в затронутом коде имеют `_camelCase`.

### Предварительные наблюдения по исходному состоянию

- В solution есть только `Ytdlp.Ui.Tests`; этот проект смешивает доменные unit-тесты, HTTP через WebApplicationFactory и
  проверки файловой SQLite. Фабрика находится в корне проекта, общих `SetupBase`/`SetupGlobal` нет.
- Корневые общие свойства и CPM уже существуют; групповые props явно импортируют корневой файл. Это нужно сохранить, а
  не вводить параллельную систему настроек.
- В CI тестируется только прежний `.Tests`; после переноса сценариев необходим явный запуск интеграционного проекта.

## Этап 2. OIDC, серверная cookie-сессия и React SSO

База этапа — коммит `37470ed`: этап 1 принят, заключительный Rider Reformat и коммит выполнены руководителем. Статус
этапа 2: реализация задач 1.1–3.3 change `authentik-sso-and-file-uploads` принята ревьюером после исправления замечаний;
коммит ожидает заключительного Reformat журнала и плана.

### Критерии приемки

- Вход проходит через настоящий OpenIdConnect middleware против управляемого тестового issuer с discovery/JWKS/token
  endpoint и проверкой PKCE. Тестовый authentication handler не заменяет проверяемую OIDC-цепочку.
- Подпись RSA, issuer, audience, срок, state, nonce и correlation проверяются; code verifier используется при обмене
  кода. Неправильный, отсутствующий или повторно используемый ответ не создает административный ticket. Небезопасный
  returnUrl не дает внешний redirect.
- Группа настраивается и принимается только из проверенных данных Authentik. Работают группы-массивы и группа, доступная
  только в UserInfo после mapping; несовпадающий UserInfo sub, отсутствие группы и группа из query не предоставляют
  доступ. Проверка группы не выполняется преждевременно до UserInfo.
- Новая EF-миграция применяется поверх действующей InitialPersistence с сохранением загрузок/истории и отзывом старых
  локальных сессий. Исторические миграции не переписываются.
- Cookie использует серверный SQLite ticket, HttpOnly и Secure в production; постоянные ключи Data Protection и
  абсолютное истечение через 12 часов сохраняются после перезапуска. Активность не продлевает срок; отзыв и отсутствие
  ticket немедленно закрывают доступ.
- TicketStore использует короткие DI scopes, не строит второй контейнер и не сохраняет access/refresh tokens провайдера.
  Ошибка записи не выдает cookie; ошибка отзыва не подтверждает успешный logout. Проверки отказов не раскрывают секреты
  в HTTP-ответе.
- Все существующие изменяющие команды защищены cookie, административной политикой и CSRF до побочных действий. API
  возвращает `401`/`403` в согласованном формате без HTML-redirect; публичные чтения остаются доступны. Прежние
  парольный login/refresh и Bearer JWT больше не дают входа.
- React заменяет парольную форму SSO-кнопкой, проверяет server session, удаляет прежние browser tokens и не создает
  новые в storage. CSRF передается в изменяющие запросы; `401` и поздние ответы не восстанавливают прежнюю сессию.
  Сетевые ошибки не изображают успешный logout.
- Настройки Authentik, группы, callback, доверенного reverse proxy и сохраняемых ключей отражены в readme/общем
  design/Docker/Compose без значений настоящих секретов.
- Код и документация проходят обязательный Rider Reformat перед коммитом, затем релевантные
  build/unit/integration/React/publish проверки. Реальный Authentik и ARM64 не считаются проверенными по одному
  fake-issuer набору или AMD64-сборке.

### Решения руководителя до ревью

- Интерактивный OIDC callback при отсутствии административной группы возвращает браузер на фиксированный локальный
  `/?authError=access_denied` без создания ticket/cookie вместо показа прямого JSON `403`. Это обеспечивает
  предусмотренный локализованный отказ на странице библиотеки. Обычные административные API сохраняют `401`/`403` JSON
  без redirects.
- Ревью проверит whitelist отображаемых authError codes, отсутствие provider/exception/identity details в URL и ответе и
  невозможность получить права через `authError` или другие query-параметры. Это уточнение протокольного UI, а не
  расширение роли или области доступа.
- После раннего чтения Program руководитель отнес настройку trusted Forwarded Headers к этапу 2: она нужна для
  правильного внешнего redirect_uri при завершении HTTPS на существующем proxy. Проверить middleware до auth,

## Этап 3. S3, публичная библиотека и ручная отправка файлов

### Критерии приемки

- Настоящий S3-адаптер проверяется через HTTP приложения с MinIO в Testcontainers, динамическим портом и изолированными bucket/ключами. Контейнер, фабрики, клиенты, потоки и временные файлы имеют явного владельца; падение проверки не оставляет ресурсы. Недоступность Docker не маскируется пропуском успешной приемки.
- Публичный плоский каталог обходит все страницы S3, показывает внешние объекты и сохраняет произвольные UTF-8 ключи. Идентификатор файла однозначно восстанавливает ключ, включая пробелы, `/`, `+`, `%` и `#`; SQLite не подменяет каталог S3.
- Публичное скачивание передает байты S3 потоком с `Content-Disposition: attachment` и безопасным именем, без загрузки всего объекта в память. Ответ S3 и поток освобождаются при завершении и обрыве клиента; после начала тела не дописывается JSON ошибки.
- Отправка требует серверной cookie-сессии, роли администратора и CSRF до чтения тела. Ровно один файл и корректное завершение multipart-формы подтверждаются до Complete/публикации; лишний файл, поле или поврежденная форма не оставляют готового объекта.
- Принимаются пустые файлы, произвольные расширения и MIME-типы с сохранением байтов. Одинаковые имена получают разные ключи и не перезаписывают внешние или ранее опубликованные объекты; ручная отправка не создает фиктивное URL-задание.
- Память ограничена при известной и неизвестной длине. Расчет частей не вводит скрытый предел из фиксированного размера части, умноженного на 10 000; технические ограничения сервера/S3 согласованы и документированы без выдуманного ограничения продукта. Граничный расчет проверяется без загрузки терабайтов, а реальный HTTP-сценарий превышает стандартный лимит тела.
- Ошибка, отмена, abort и неопределенный результат Complete обрабатываются с проверкой собственного уникального ключа, метаданных идентичности и размера. Очистка затрагивает только ресурсы этой отправки и не удаляет подтвержденный готовый объект по одному сетевому исключению.
- Отсутствие объекта отделено от отсутствия bucket, запрета доступа и сетевой ошибки. Поздняя очистка прежней публикации приложения не удаляет следующую публикацию с другим UUID/ключом; существующие публикации и история заданий сохраняют предусмотренные guards. Атомарность удаления против внешнего writer того же ключа не обещается без фактической поддержки хранилищем.
- Задача change 4.4 принимается только в реализованной части: URL-очередь, queued/retry и recovery остаются этапам 4–6. Готовность S3 и ручных файлов не означает готовности медиапроцессов.

Для проверки расчета multipart используется текущая [документация Amazon S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html): до 10 000 частей, часть от 5 MiB до 5 GiB (последняя может быть меньше), объект до 48,8 TiB. Это границы API Amazon S3, а не обещание такой емкости конкретной версии MinIO или введенный лимит продукта.

#### R6 — P2 — поврежденная форма ошибочно считается недоступностью S3

- Статус: `fixed`; исправление независимо перепроверено после Rider Reformat на обоих MinIO images.
- Файлы и доказательство: в ранней стабильной версии `src/Ytdlp.Ui/Infrastructure/Storage/S3StorageUpload.cs` вызов `input.ReadAsync` находится под общим catch `IsStorageError`, включающим `IOException`; endpoint преобразует полученный `StorageUnavailableException` в `503`. Реальный [MultipartReaderStream ASP.NET Core 10.0.12](https://github.com/dotnet/aspnetcore/blob/v10.0.12/src/Http/WebUtilities/src/MultipartReaderStream.cs#L236) при неожиданном конце тела бросает именно `IOException`. Исключение описывает повреждение входной формы, а не отказ S3.
- Воспроизведение: отправить авторизованный запрос с правильным CSRF, заголовками единственной file-part и оборванной завершающей boundary; подготовлен `UploadFailureTests.TruncatedMultipartIsBadRequestAndNeverCompleted`. На момент регистрации ревьюер этот тест еще не запускал, доказательство основано на конкретном потоке исключения в коде и официальном исходнике reader.
- Требуемое поведение: `400 invalid_upload`, без Complete и готового объекта; незавершенные собственные части очищаются. Ошибка диска или S3 сохраняет отдельную обработку `503`.
- Ответ разработчика: замечание принято; IOException непосредственно входного `ReadAsync` и обоих `ReadNextSectionAsync` преобразован в ошибку формы, disk/S3 ошибки сохраняют отдельную обработку. Один catch `InvalidDataException` не исправлял оборванную boundary. Ревьюер отдельно исправил свое первоначальное неверное предположение о наследовании `InvalidDataException` от `IOException`: этот тип наследует `SystemException`.
- Решение руководителя: обязательное исправление принято; оборванная multipart boundary является ошибкой входного запроса, а не недоступностью S3. Разделение ошибок источника и disk/S3 подтверждено.
- Проверка исправления: `TruncatedMultipartIsBadRequestAndNeverCompleted` прошел в обоих независимых Storage-наборах 23/23; подтверждены `400`, отсутствие Complete/готовых объектов/частей и очищенный scratch. Сценарии поврежденной первой boundary и заголовков до обращения к storage также прошли в non-Storage 121/121.

#### R7 — P1 — MinIO игнорирует условие удаления и теряет замененный объект

- Статус: `accepted` по арбитражу руководителя; первый фактический набор MinIO у разработчика прошел 19/20 и выявил реальное ограничение сервера, но исходный негативный сценарий требовал поведения сверх specs. Ревьюер независимо подтвердил ограничение и обязательные guards на обоих images.
- Файл и доказательство: `src/Ytdlp.Ui/Infrastructure/Storage/S3LibraryStorage.cs`, `DeleteAsync` передает `DeleteObjectRequest.IfMatch=file.ETag`, но готовый закрепленный MinIO 2025.7.23 это условие не соблюдает. В `Storage/DeletionTests.ConditionalDeletePreservesConcurrentReplacement` fault client после HEAD записывает новый объект под прежним ключом, затем выполняет реальный DeleteObject. По сообщению разработчика получен `204` и replacement удален.
- Первоначально требуемое поведение: изменившийся объект сохраняется, API возвращает конфликт, собственная публикация не считается подтвержденно удаленной. Одного наличия If-Match в SDK request недостаточно без проверки фактического сервера. Требование атомарной защиты внешней гонки впоследствии снято по приведенному ниже арбитражу; защита поколений приложения остается обязательной.
- Ответ разработчика: первоначальный дефект признан; после арбитража сохранен честный capability probe, добавлены проверка новой публикации с другим ключом и преобразование реального `412` в `409` на границе SDK. Проверка metadata до удаления сохраняется; документировано отсутствие гарантии внешней atomic race.
- Контраргумент руководителя: обязательный сценарий `download-lifecycle/spec.md:166` защищает новую публикацию приложения от поздней очистки прежней; новое поколение получает другой UUID и ключ. Требование атомарного DELETE против внешнего writer, заменившего тот же ключ между HEAD и DELETE, в specs отсутствует. Обязательное versioning или upgrade существующего MinIO добавляли бы новое условие продукта.
- Ответ ревьюера: после повторного чтения specs контраргумент принят; первоначальный критерий был шире согласованного контракта. Факт поведения MinIO остается доказанным ограничением, но сам по себе не блокирует MVP. Требуются неизменяемые собственные ключи, metadata pre-check и проверка old/new публикаций приложения; If-Match нельзя описывать как доказанную защиту внешней гонки.
- Решение руководителя: `accepted` с документированным ограничением и capability probe, без заявления `fixed` и без ослабления обязательной защиты поколений. Документация убирает обещание CAS для неподдерживаемого MinIO и закрепляет собственное неизменяемое пространство ключей; versioning не становится новым обязательным условием.
- Проверка: оба независимых набора 23/23 подтвердили `LateDeletionOfOldPublicationCannotTouchNewPublicationKey` и metadata pre-check. В обоих TRX capability probe явно сообщает, что проверенный MinIO игнорирует If-Match; это не выдается за исправление. Unit-проверка SDK `412 → StorageConflictException` также прошла в 198/198.

### Критерии приемки PostgreSQL и сохраняемого API

- Production API заданий использует PostgreSQL и существующий доменный автомат вместо DemoStore. Логическая загрузка, первая попытка и намерение поставить ее в очередь сохраняются атомарно; HTTP завершается после постановки, без фиктивного скачивания или завершения.
- Исходная строка URL хранится отдельно и не теряется при нормализации. Сравнение удаляет только внешние пробелы и технические различия схемы/host/стандартного порта; регистр пути, query и порядок параметров остаются значимыми. Разные ссылки не объединяются по ID ролика. Невалидный ввод не создает записей.
- Дубликат ожидающего, активного, отменяемого, Failed/Canceled или доступного Completed задания возвращает понятный конфликт с ID существующей загрузки. Уникальный индекс PostgreSQL остается окончательной защитой, а не только предварительный SELECT.
- Повтор Deleted через создание по URL и через retry использует одно старое download ID, исходный URL и прежнюю историю, новый номер попытки и новую публикацию/рабочее поколение по правилам агрегата. Failed/Canceled требуют явной команды retry; недопустимая команда не создает лишней попытки.
- Одновременные create, create/retry и retry/cancel не создают двух логических загрузок или активных попыток. Обновление состояния/версии и запись попытки/намерения атомарны на настоящей PostgreSQL; stale request не меняет уже принятое состояние. Ошибки ограничений различаются по SQLSTATE, а не локализованному сообщению. Проверки используют разные HTTP-запросы и короткие DbContext scopes, а не общую tracked-сущность.
- Последовательная очередь сохраняется между хостами/рестартами, выбирает ожидающее задание в согласованном порядке и не выдает второе одновременно. В этом этапе проверяется сохраняемая постановка/выбор; настоящий worker, процессы медиа и сквозное восстановление остаются этапам 5–6.
- История попыток/этапов, FailedState/ResumeState, отмена и allowedActions выводятся из сохраняемых данных и правил автомата. Сохраняются прежние результаты и история; новые команды не изображают выполненную очистку или публикацию без внешнего действия.
- Completed результат перед разрешением нового скачивания проверяется в S3: подтвержденный NoSuchKey в доступном bucket допускает ResultDeleted и одну новую попытку. 403, timeout, сеть, отсутствие bucket и несовпадение metadata не объявляют удаление; S3 вызывается вне транзакции, затем версия/состояние проверяются повторно. Публичный GET не ставит задания в очередь.
- Все endpoints заданий и истории требуют действующую cookie/роль; изменяющие команды дополнительно требуют CSRF. Анонимный посетитель не получает закрытых заданий/URL/истории и не меняет очередь. API сохраняет JSON-ошибки без redirect; измененный контракт документирован без обещания еще не подключенного worker.
- Единственный Npgsql provider и новая начальная PostgreSQL-миграция заменяют действующие SQLite-миграции/interceptor и fallback. UUID, внешние связи, unique URL/номер попытки/одна активная попытка, optimistic Version и progress constraints реально проверяются в PostgreSQL. Даты хранятся как UTC `timestamp with time zone`, без прежнего конвертера миллисекунд.
- Серверный ticket store с нейтральным именем использует ту же PostgreSQL, сохраняя protected ticket, 12 часов absolute, отзыв/restart и выдачу cookie только после записи. Сбой сохранения не выдает сессию и не изображает успешный logout; старая cookie не получает доступа в чистой БД даже при сохраненном key ring.
- SetupGlobal владеет одним PostgreSQL Testcontainer набора с динамическим портом/готовностью; фабрика/SetupBase владеет изолированной БД сценария и временными файлами. Restart использует явно общую БД и ключи. Cleanup работает после assertion/setup failure; пользовательские БД не задействуются. MinIO остается отдельным управляемым контейнером Storage-набора. Недоступный Docker не превращается в пропущенный успешный тест.
- Глобальный claim сериализуется короткой PostgreSQL-транзакцией; один лишь `SKIP LOCKED` выбранной строки не доказывает ограничение одного исполняемого задания. Два claim с несколькими pending должны дать не более одного work item. Распределенная очередь и несколько одновременно работающих экземпляров приложения не добавляются.
- Конфигурация/Compose используют внешний PostgreSQL; сохраняются volumes ключей/рабочих файлов и данные на стороне сервера БД. Недоступность PostgreSQL или ошибка миграции не объявляют готовность и не включают другой provider. Старый SQLite-файл остается без изменений; connection string/ошибка startup не раскрывает пароль. Runtime и publish не содержат действующей SQLite-зависимости.

#### R8 — P2 — допустимый длинный URL не помещается в PostgreSQL B-tree

- Статус: `fixed`; исходное воспроизведение разработчика и независимая проверка исправления разделены ниже.
- Файлы и доказательство: `Infrastructure/Persistence/AppDbContext.cs` и новая начальная миграция создают unique B-tree непосредственно по неограниченному `NormalizedUrl`; `Features/Downloads/SourceUrl.cs` принимает допустимую длинную HTTP-ссылку. [Официальная документация PostgreSQL](https://www.postgresql.org/docs/current/btree.html) ограничивает размер записи B-tree примерно третью страницы после применимого сжатия, поэтому допустимость `text` не гарантирует возможность индексировать весь URL.
- Воспроизведение разработчика: HTTP `ValidLongIncompressibleUrlCanBeDurablyQueued`, query содержит 8192 случайных hex-символа, ответ `500`; PostgreSQL вернула SQLSTATE `54000`, `index row requires 8240 bytes, maximum 8191`. Один повторяемый символ для проверки не годится из-за сжатия. Ревьюер не запускал .NET параллельно разработчику и не приписывает себе этот результат.
- Требуемое поведение: валидный URL сохраняется и ставится в очередь; повтор/конкуренция/рестарт сохраняют ту же идентичность. Не вводится искусственный продуктовый URL cap; длинная query не должна приводить к неожиданному `500` из индекса.
- Ответ разработчика: дефект подтвержден; реализован unique ключ SHA-256 фиксированных 32 байт с constraint длины при сохранении полного нормализованного текста. Только наша еще не закоммиченная начальная PostgreSQL-миграция регенерирована под чистую БД.
- Решение руководителя: исправление обязательно; SHA-256 вычисляется централизованно на persistence boundary без pgcrypto/отдельного hash service. Поиск учитывает hash и точный нормализованный текст; теоретический collision дает технический `409`, не объединяет разные URL и не раскрывает чужой ID.
- Проверка исправления: после Rider независимо прошел `ValidLongIncompressibleUrlCanBeDurablyQueued`: 8192 случайных hex-символа, три конкурентных запроса с одним `201` и двумя `409`, точная исходная строка после рестарта и повторный дубликат. `HashCollisionDoesNotExposeAnotherDownloadIdOrMergeDifferentUrl` также прошел: искусственно созданный collision дает `409 url_conflict`, не содержит чужого ID и не добавляет загрузку. Оба сценария входят в независимые PostgreSQL 148/148, без пропусков.

### Критерии приемки

- Настоящий BackgroundService использует сохраняемую PostgreSQL queue, короткие DI/DB scopes и один последовательный обработчик всей попытки. Claim/intents/history фиксируются до внешних действий, переходы и результаты — после них с проверкой актуальных attempt/publication/Version. Ошибка процесса или БД не изображается успешной обработкой.
- Metadata yt-dlp представляет отдельный завершенный публичный ролик: playlist, текущий и запланированный live отклоняются до скачивания. Отдельный ролик с playlist context не превращается в загрузку плейлиста; завершенный архив эфира не запрещается автоматически как live.
- План выбирает видео с аудио не выше 1080p, предпочитает подходящий MP4 и допускает исходный fallback без перекодирования. Audio-only, video-only без подходящей пары и отсутствие допустимого качества не дают ложного готового результата. Размер/длительность ролика не получают нового продуктового cap.
- Готовый совмещенный файл не объединяется повторно. Отдельные дорожки скачиваются без скрытого auto-merge/fixup yt-dlp, затем FFmpeg копирует потоки без transcode в совместимый контейнер. FFprobe проверяет наличие audio/video и фактический результат; расширение соответствует контейнеру, готовность фиксируется после проверки и безопасного переименования.
- URL передается одним ArgumentList-аргументом с защитой от восприятия как options, без shell и подхвата постороннего yt-dlp config. Форматы/имена/пути не становятся произвольными CLI-командами. stdout/stderr читаются одновременно с ограниченной памятью, включая длинную строку; отмена останавливает дерево процесса и ожидает завершения чтения/процессов до очистки.
- Workspace принадлежит конкретным download ID и generation; metadata/title не используются как неподконтрольный локальный путь. Сохраненные артефакты описывают проверенные файлы и не выходят за свой каталог. Ошибка Prepare/Upload сохраняет пригодные входы для следующего этапа надежности, без удаления по возрасту.
- Публикация использует заранее сохраненный собственный ключ и publication ID, multipart не вводит file-size cap. S3 подтверждается metadata/размером/контрольной суммой по согласованному контракту до CleaningUp; неопределенный исход проверяется перед повтором. Нельзя объявить Completed или удалить локальные входы до подтверждения объекта. Очистка не касается чужой операции/нового поколения.
- Progress отражает фактические данные выбранных дорожек/этапа; неизвестный общий размер означает null, а не таймерный процент. История содержит этап, попытку, ошибки и точку продолжения; после подтверждения файла PublicationState=Available совместим с незавершенной/неудачной локальной очисткой.
- Проверки исполняют настоящий worker и HTTP/PostgreSQL pipeline с управляемой границей внешних инструментов; process runner проверяется реальными контролируемыми процессами. Успешное завершение подтверждается доступными байтами S3 и очищенным собственным workspace. Изоляция тестов отключает/подменяет только требуемую границу, не auth/DB/FSM проверяемого приложения.
- Полные retry/recovery/cancel/delete протоколы принимаются в этапе 6, полный UI — в 7, runtime packaging и обе архитектуры — в 8. Проверенные локальные процессы не объявляются готовностью runtime образа; неподтвержденные среды фиксируются отдельно. Вопрос первичного own DELETE и одной обработки остается в журнале этапа 6.

## Этап 6. Повторы, восстановление, отмена и удаление

### Критерии приемки

- Recovery выполняется после PostgreSQL migrations и до запуска queue/worker. Прерванные Downloading/Preparing/Uploading/CleaningUp/Deleting/Canceling становятся Failed с прежними attempt/history, FailedState/ResumeState и файлами для ручного повтора; обычные ожидающие Queued остаются в очереди. Восстановление не запускает прерванную обработку автоматически.
- Retry проверяет физическое наличие, size и SHA-256 пригодных артефактов. Подтвержденные успешные этапы не повторяются; история новой попытки объясняет reuse и возврат к самому раннему необходимому этапу при missing/corrupt input. FailedState прежней ошибки и прежняя история сохраняются. Cleanup/Delete/Cancel не откатываются к скачиванию при частичной очистке или отсутствующих файлах.
- Неопределенный Upload сначала согласуется с уже сохраненными key/publication/download/size/SHA и S3. Подтвержденный готовый объект позволяет продолжить cleanup без повторной отправки, в том числе если локальный prepared file уже утрачен. 403, timeout, сеть, отсутствие bucket и несовпадение metadata не превращаются в подтвержденное отсутствие или разрешение перезаписать объект.
- Намерение и идентичность внешнего действия сохраняются до I/O. Fault-сценарии до/после внешнего успеха и до/после записи БД не создают повторную публикацию, ложный Deleted/Completed или потерю подтвержденной истории. Известный MPU и неизвестный исход Initiate/Complete согласуются только в собственной операции; чужие объекты/parts не очищаются.
- Обе очередности Uploading→CleaningUp против cancel проверяются на PostgreSQL через настоящий pipeline. Победившая cleanup дает cancel409; победивший Canceling не разрешает поздний Upload success и очищает только свою незавершенную публикацию. Cancel запрещен в CleaningUp и Failed/Queued ResumeCleaningUp и отсутствует в allowedActions.
- Canceled выставляется лишь после подтвержденного прекращения I/O и очистки собственных ресурсов. Ошибка остановки/очистки сохраняет Failed/ResumeCanceling; повтор отмены не создает новую работу. После Canceled/Deleted новая попытка получает новый publication/workspace, сброшенный MediaPlanJson и свежие artifact IDs; запоздалый старый результат/cleanup не касается нового поколения.
- Неподтвержденная остановка процесса дает отдельный typed failure: файлы не очищаются, Canceled/Completed не симулируются, следующий claim не начинается. Согласован простой StopApplication/stop-claim barrier без process registry; persist failure также не должен снять барьер. User cancel сохраняет ResumeCanceling, host shutdown — Interrupted исходного этапа без synthetic RequestCancel. Безопасный restart/recreate контейнера с завершением всей PID namespace явно отделен от перезапуска одного host в прежней namespace.
- Собственное удаление проходит через общую последовательную очередь и сохраненные Deleting intent/history с API202; внешнее удаление без job остается синхронным. Initial DELETE, retry deletion и worker не создают вторую обработку. Ответ202 не называется подтвержденным удалением; клиент показывает pending, пока S3/DB не подтвердят завершение. CleaningUp и DB publication/state guards дают409 до enqueue. Наблюдение S3 metadata/availability выполняет worker после202: ошибка дает Failed/ResumeDeleting с publication_changed/storage_unavailable и сохранным объектом; это не прежний immediate HTTP409/503.
- Анонимные GET библиотеки/content не создают попытку и не меняют очередь. Все команды/retry/cancel/delete требуют прежние cookie/роль/CSRF, ошибки остаются JSON без redirect. Отказ БД/хранилища не объявляет успех, исходный URL/ID/история не теряются при повторе.
- Проверки используют настоящую PostgreSQL и MinIO, управляемые внешние инструменты и fault gates; отдельные настоящие процессы подтверждают нормальный kill/drain. Test owners освобождают контейнеры/БД/файлы при ошибке; чужие поколения, buckets и параллельная работа не затрагиваются. Предыдущие runtime/selector/codec сценарии остаются регрессиями, а полный UI и обе production архитектуры завершаются этапами 7–8.
