# Журнал ревью MVP

Ревьюер проверяет каждый этап независимо от разработчика. Руководитель принимает решения по разногласиям и разрешает
этапный коммит после проверки исправлений.

## Порядок учета замечаний

- Замечания получают сквозные идентификаторы `R1`, `R2` и далее, приоритет, область этапа, файл и воспроизводимое
  доказательство.
- Для каждого замечания фиксируются требуемое поведение, ответ разработчика, решение руководителя и статус `open`,
  `fixed` или `accepted`.
- `fixed` означает, что исправление перепроверено ревьюером; `accepted` означает, что руководитель принял доказанный
  контраргумент или явно согласовал исключение.
- Проверки, выполненные разработчиком, и независимо выполненные проверки ревьюера указываются раздельно. Сборка не
  считается проверкой запуска.
- Исходные пробелы последующих этапов не являются блокерами текущего этапа только из-за их наличия до его начала.

## Этап 1. Структура репозитория и тестовая инфраструктура

Статус: этап принят после исправления R1/R2 и независимой перепроверки; итоговый журнал ожидает обязательного Reformat
перед коммитом.

### Критерии приемки

- Настройки solution, props и CPM соответствуют `dotnet-repository-structure`: каждый проект включен в solution,
  Solution Items указывают на существующие файлы, вложенные props импортируют родительские; тестовые пакеты не попадают
  в production.
- `.Tests` содержит модульные сценарии; HTTP-pipeline, хост и настоящая файловая SQLite с миграциями проверяются в
  `.IntegrationTests`.
- `CustomWebApplicationFactory` находится в `Tools`, `SetupBase` и `SetupGlobal` — в отдельных файлах корня
  интеграционного проекта; настройка хоста, сценарии и владение ресурсами разделены по `dotnet-integration-tests`.
- Сценарии не зависят от порядка запуска, очистка выполняется после падения assertions, scoped-сервисы не живут весь
  набор; общие изменяемые ресурсы исключают параллельный запуск без изоляции.
- Сохраняются значимые сценарии старого набора, включая миграции, перезапуск, гонки refresh и запрет отмены очистки. На
  этом этапе контракт авторизации и мокового API не меняется.
- SDK закреплен согласованно в `global.json`, Docker и документации; CI выполняет оба тестовых проекта и проверяет
  публикацию с готовым React.
- Приватные поля в затронутом коде имеют `_camelCase`.

### Предварительные наблюдения по исходному состоянию

- В solution есть только `Ytdlp.Ui.Tests`; этот проект смешивает доменные unit-тесты, HTTP через WebApplicationFactory и
  проверки файловой SQLite. Фабрика находится в корне проекта, общих `SetupBase`/`SetupGlobal` нет.
- Корневые общие свойства и CPM уже существуют; групповые props явно импортируют корневой файл. Это нужно сохранить, а
  не вводить параллельную систему настроек.
- В CI тестируется только прежний `.Tests`; после переноса сценариев необходим явный запуск интеграционного проекта.

### Замечания по diff

#### R1 — P2 — В окружении Testing не подключаются собранные static web assets

- Файл: `tests/Ytdlp.Ui.IntegrationTests/Tools/CustomWebApplicationFactory.cs`, настройка окружения в
  `ConfigureWebHost`.
- Доказательство: независимый
  `dotnet test tests/Ytdlp.Ui.IntegrationTests/Ytdlp.Ui.IntegrationTests.csproj -c Release --no-build --verbosity minimal`
  воспроизвел `404` вместо `200` в `HelloApplicationTests.FrontendAndItsCompiledAssetsAreServedByApplication` для `/` и
  `/Client-route` (assertion на строке 38 первоначального diff). В логе: WebRootPath отсутствует в каталоге исходников.
  Готовый `dist` существует, поэтому это не пропуск frontend build.
- Требуемое поведение: настоящий тестовый HTTP-pipeline должен раздавать подготовленный UI и assets в окружении Testing,
  как и проверяемая публикация приложения.
- Ответ разработчика: проблема подтверждена независимо; добавлен `UseStaticWebAssets` в фабрике.
- Решение руководителя: замечание признано обязательным исправлением этапа 1; исправление принято после зеленых
  post-format проверок.
- Перепроверка ревьюера: полный интеграционный набор 89/89 и точечные UI-регрессии прошли; `/` и `/client-route`
  возвращают подготовленный UI и JavaScript.
- Статус: `fixed`.

#### R2 — P2 — Фоновый Data Protection обращается к пользовательскому key ring

- Файл: `tests/Ytdlp.Ui.IntegrationTests/Tools/CustomWebApplicationFactory.cs`, регистрация Data Protection.
- Доказательство: тот же независимый прогон содержит ошибки `KeyRingProvider`/`DpapiXmlDecryptor` с обращениями к
  пользовательскому `AppData/Local/ASP.NET/DataProtection-Keys`. Замена provider на ephemeral не изолировала
  зарегистрированный фоновый key manager; он получил DPAPI/Access denied вне временного каталога тестов.
- Требуемое поведение: тестовый хост полностью использует собственные временные ключи/хранилища и не читает и не
  изменяет пользовательский key ring.
- Ответ разработчика: подтверждено; `PersistKeysToFileSystem` направляет key manager во временный каталог конкретного
  теста, включая хосты с явно заданным путем БД.
- Решение руководителя: замечание признано обязательным исправлением этапа 1; исправление принято после независимой
  проверки.
- Перепроверка ревьюера: точечный прогон трех UI/error-сценариев с TRX прошел 3/3. Проверен отчет с захваченными логами
  окружения Testing (109 924 символа): нет пользовательского пути `ASP.NET/DataProtection-Keys`, ошибок
  `DpapiXmlDecryptor` и ошибок чтения key ring. Полный набор также прошел 89/89.
- Статус: `fixed`.

### Принятые решения по реализации

- Новая фабрика/клиент на каждый обычный тест допустимы скиллом. Эта модель изолирует singleton DemoStore; общая фабрика
  только ради шаблона не требуется. `SetupGlobal` владеет общим временным каталогом, `SetupBase` — ресурсами теста.
- При ошибке `CreateClient` фабрика освобождается в catch. Отдельно настроенные startup/restart/options/time-сценарии
  владеют хостами и scoped-контекстами через using/await using; каталоги startup/restart удаляются в TearDown. SQLite
  использует `Pooling=false`.
- По решению руководителя production pipeline дополнен `AddProblemDetails`/`UseExceptionHandler`: переход тестового
  хоста с Development на Testing выявил пробрасывание необработанной DbUpdateException вместо HTTP-ответа. Существующий
  тест отказа записи теперь проверяет `500`, `application/problem+json`, статус в JSON и отсутствие access/refresh
  token, пароля, SQL trigger text и имен исключений в теле ответа.

### Итог этапа

Замечания R1/R2 исправлены и перепроверены, открытых претензий к коду этапа 1 нет. Ревьюер рекомендует приемку;
руководитель принял этап после Docker smoke. Этап готов к отдельному коммиту после заключительного Reformat журнала и
плана. Эта приемка не означает готовности OIDC, реального S3, очереди и медиапроцессов следующих этапов.

## Исходные вопросы для последующих этапов

- Календарный Docker-тег: в исходной `.github/workflows/ci.yml` используется `--date=format`, поэтому `TZ=Europe/Moscow`
  не обеспечивает преобразование даты коммита. Указание уже есть в `REVIEW-FOLLOWUPS.md`; проверить исправление на этапе
  CI/поставки с коммитом около московской границы дня. Это не блокер этапа 1 при отсутствии изменения логики тегов.
- Полный runtime yt-dlp/FFmpeg, очередь, реальное S3 и OIDC пока не реализованы. Это запланированная работа следующих
  этапов; приемка адаптации тестовой структуры не означает готовности этих возможностей.
