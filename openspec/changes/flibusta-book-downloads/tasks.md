# Tasks

План относится только к Flibusta. OPDS требует отдельной будущей проработки. Эти задачи не означают готовность
общей очереди или S3 в базовом коммите `f34cc88`; интеграция зависит от их принятой реализации в основном MVP.

## 1. Основа интеграции и проверка источника

- [ ] 1.1 Подключить change поверх принятой общей сохраняемой очереди, публикации S3 и восстановления, сохранив один worker. Проверка: существующие сценарии постановки, последовательного выполнения, повторов и публикации основного MVP проходят до добавления Flibusta; конкретная база интеграции записана в design.
- [ ] 1.2 Проверить анонимный ответ `/b/{id}/fb2` на тестовой книге: формат, Content-Type, имя и кодировка ZIP, redirects и доступ из целевого окружения. Проверка: наблюдения записаны в design с датой и ограничениями; локальные синтетические fixtures воспроизводят подтвержденный ответ без сохранения полной внешней книги в репозитории.
- [ ] 1.3 Добавить получение и подготовку Flibusta в существующие точки выполнения этапов, сохранив общий автомат. Проверка: интеграционный сценарий с книгой и роликом выполняет их последовательно; для книги не вызываются yt-dlp/FFmpeg, для ролика сохраняется прежний обработчик.

## 2. Идентичность и создание задания

- [ ] 2.1 Добавить сохраняемую идентичность источника и миграцию уникальности: прежним заданиям оставить ключ из NormalizedUrl, книгам назначать ID Flibusta. Проверка: миграция настоящей файловой SQLite сохраняет ID, URL, попытки и историю; существующие значения enum не изменены.
- [ ] 2.2 Реализовать серверное распознавание карточки и нормализацию ID с сохранением исходной ссылки. Проверка: тесты принимают разрешенные `/b/{id}` и конечный `/`, учитывают query/fragment только как часть исходной строки, отклоняют credentials и пути скачивания/чтения/автора/поиска, не передают отклоненный URL Flibusta в yt-dlp.
- [ ] 2.3 Подключить поиск дубликата, создание и повтор после Deleted по идентичности книги. Проверка: HTTP/SQLite-тесты двух зеркал, разных изданий, Failed/Canceled, Deleted и конкурентных запросов сохраняют одно задание и одну активную попытку; сценарии URL-дубликатов yt-dlp проходят без изменения семантики.
- [ ] 2.4 Обновить в readme контракт существующего POST /api/downloads и ошибки карточки/дубликата Flibusta. Проверка: примеры содержат только URL, соответствуют проверенным HTTP-ответам и сохраняют текущие требования авторизации.

## 3. Потоковое получение FB2

- [ ] 3.1 Добавить BaseUrl/AllowedHosts, проверку конфигурации и выделенный HTTP-адаптер, строящий адрес FB2 по ID. Проверка: локальный HTTP-источник фиксирует запрос только к настроенному адресу; смена BaseUrl не меняет идентичность задания, а неразрешенные redirects и неверная конфигурация отклоняются.
- [ ] 3.2 Реализовать потоковое сохранение ответа, отмену и ошибки получения без автоматической смены формата. Проверка: локальные ответы ZIP/FB2, HTML с 200, 4xx/5xx, обрыв, timeout и отсутствие Content-Length дают ожидаемые состояния и не публикуют ошибочный файл; неизвестный процент остается null, тело целиком в RAM не накапливается.
- [ ] 3.3 Документировать настройки Flibusta, анонимный clear-web доступ и диагностику отказов в readme. Проверка: примеры настроек проходят валидацию, не содержат секретов и не обещают аккаунт, Tor, OPDS или переход на другой формат.

## 4. Подготовка, имя и метаданные

- [ ] 4.1 Реализовать потоковое выделение ровно одного обычного FB2 из ZIP либо проверку готового FB2. Проверка: тесты принимают один FB2 с посторонними вложениями и готовый FB2; поврежденный ZIP, ноль/несколько FB2, неподходящий XML, ссылки и пути выхода из каталога дают Failed без записи вне workspace и без публикации.
- [ ] 4.2 Сохранять исходное имя отдельно от внутреннего пути артефакта и исходные байты FB2. Проверка: кириллица, пробелы, имя из ZIP и filename ответа проходят round-trip; отсутствующее/небезопасное имя дает понятную ошибку, разные книги с одинаковыми именами не перезаписываются, контрольные суммы содержимого совпадают.
- [ ] 4.3 Извлекать nullable title из метаданных FB2 без пересериализации и внешних сущностей. Проверка: один/несколько авторов, только название, отсутствующее или пробельное название дают ожидаемый title/null; метаданные не меняют имя и байты, а DTD и внешние сущности не читают локальные или сетевые ресурсы.
- [ ] 4.4 Подключить пригодность книжных артефактов к общей точке продолжения и описать правила FB2/ZIP в readme. Проверка: после ошибки подготовки пригодный вход используется повторно, после доказанной непригодности повтор получает источник заново; документация отражает один выходной FB2 и отсутствие конвертации.

## 5. Публикация и nullable title в API/UI

- [ ] 5.1 Добавить миграцией исходное имя артефакта и nullable snapshot title/признаки объекта в данные публикации. Проверка: миграция существующей SQLite не теряет публикации, новые поля старых файлов остаются null, snapshot имени/title сохраняется до внешнего действия и восстанавливается после потери ответа S3.
- [ ] 5.2 Публиковать подготовленный FB2 общим протоколом с уникальным ключом и исходным именем. Проверка: изолированный MinIO подтверждает точные байты, два одноименных результата, правильное имя публичного скачивания, отсутствие лишних вложений и отсутствие готового объекта после отказа подготовки.
- [ ] 5.3 Дополнить полный S3 listing nullable title своих подтвержденных публикаций по полному ключу и совпадающим признакам объекта. Проверка: MinIO/SQLite-тесты покрывают все страницы, внешние и ручные файлы, рестарт, удаление объекта извне, совпадение basename и изменение fingerprint; каталог не делает HEAD для каждой строки и не создается из БД.
- [ ] 5.4 Добавить nullable title в публичный DTO/тип клиента и известное имя в проекцию задания; использовать `title ?? name` в каталоге и `title ?? fileName ?? url` для книги. Проверка: HTTP/React-тесты title/null, задания до получения файла, публичного просмотра, скачивания и подписей действий подтверждают исходное имя файла и прежние права управления.
- [ ] 5.5 Обновить EN/RU-ресурсы, readme API библиотеки/заданий и описание имени/title. Проверка: строки ошибок/валидации берутся из ресурсов, примеры явно возвращают title:null при отсутствии данных, ни интерфейс, ни сервер не записывают filename в title как fallback.
