# Design

## Context

Мотивация и согласованный объем приведены в [proposal.md](proposal.md), проверяемый контракт — в
[specs/](specs/). OPDS пользователь оставил для отдельной проработки.

План ведется в отдельном worktree на ветке `codex/flibusta-plan` от `f34cc88` — последнего отдельного коммита
планирования OpenSpec в `codex/dev` на момент выбора базы. В этой базе API заданий и библиотеки использует `DemoStore`.
Есть `DownloadRecord.Title`, автомат, SQLite-модели попыток, артефактов и публикаций, но это не готовый worker.
`ArtifactKind` содержит видеоориентированные значения; публичная модель файла содержит `name`, но не `title`.

Основной MVP и [authentik-sso-and-file-uploads](../authentik-sso-and-file-uploads/proposal.md) реализуются параллельно.
При исследовании также просмотрен последующий `1512e0a`: там уже есть `ILibraryStorage`, полный S3 listing,
потоковое чтение и связь `ObjectKey → StorageTransferRecord → DownloadRecord`. Эти реализации не включены в базу
данного worktree. Интеграция Flibusta зависит от принятой общей очереди, публикации и восстановления; дублировать их
в этом change не требуется. Общие правила этапов и поколений рабочих каталогов остаются из
[общего технического проекта](../../design.md).

## Goals / Non-Goals

**Goals:**

- Добавить два варианта получения и подготовки в общую цепочку: существующее медиа и книгу Flibusta.
- Сохранить отдельные понятия: исходная ссылка, идентичность источника, локальный путь, исходное имя и nullable title.
- Сохранять пригодные артефакты и данные публикации для повторов, не меняя состав публичного каталога.

**Non-Goals:**

- Вторая очередь, отдельный worker или переписывание общего автомата.
- Универсальный OPDS-клиент, динамические плагины источников и каталог книг внутри UI.
- Новая БД, отдельный сервис распаковки, конвертер или новая библиотека для чтения FB2.

## Decisions

### 1. Идентичность источника отдельно от URL

Техническое решение плана: сохранять вид источника и ключ сравнения. Для yt-dlp ключом остается текущий
нормализованный URL, для Flibusta — канонический десятичный ID записи. `OriginalUrl` и `NormalizedUrl` сохраняют свои
значения и не используются как адрес запроса Flibusta. Уникальность обеспечивается парой вида и ключа источника в БД,
а не только предварительным поиском в API. При конфликте возвращается существующее задание по общей семантике `409`.

Миграция присваивает прежним заданиям вид yt-dlp и ключ из сохраненного `NormalizedUrl`, заменяя соответствующий
уникальный индекс без изменения ID, URL и истории. Индекс одной активной попытки остается общим. Автоматическое
переопределение вида старых заданий по их URL не выполняется.

Альтернатива — записывать синтетический URL книги в `NormalizedUrl` — смешала бы нормализацию с идентичностью источника
и привязала бы сравнение к выбору адреса. Строка вида «каталог + запись OPDS» в этот план не вводится.

### 2. Узкий HTTP-адаптер Flibusta

Валидация выполняется на сервере. Принимается HTTP(S) URL без credentials, с разрешенным host и путем
`/b/<положительный ID>`; конечный `/` допускается. Query и fragment карточки не меняют ID и не попадают в адрес
скачивания; исходная строка сохраняется. Пути чтения, скачивания, автора и поиска разрешенного домена отклоняются
до постановки, а не передаются yt-dlp.

Предлагаемые настройки: `Flibusta:BaseUrl` и `Flibusta:AllowedHosts`; начальные значения — `https://flibusta.is/`
и `flibusta.is`. BaseUrl — HTTP(S) origin без credentials, query и fragment. Списки host сравниваются точно,
без сопоставления по подстроке; hostname запроса берется из конфигурации. Неполная или некорректная конфигурация
не должна приводить к использованию произвольного введенного URL. Настройки проверяются при запуске.

Адаптер строит `/b/{id}/fb2` на BaseUrl и получает ответ выделенным `HttpClient` с потоковым чтением, отменой и
транспортным timeout. Redirect обрабатывается явно и ограниченно: допускаются только настроенный origin или
явно разрешенные clear-web origin. Cookie приложения, OIDC-заголовки и пользовательские credentials не передаются.
Ответ на ошибку, страницу входа или блокировки завершает попытку ошибкой; обходы и fallback на другой формат отсутствуют.

Выбран прямой HTTP-запрос по известному ID. Разбор HTML нужен был бы для дополнительных данных страницы, но название
берется из самого FB2. OPDS и запуск yt-dlp для книги добавили бы независимые механизмы вне согласованного объема.

### 3. Подготовка как обработчик общего этапа

Общий worker выбирает получение и подготовку по виду источника, используя существующие точки выполнения этапов.
Нужны только два известных варианта; публичный реестр плагинов не проектируется. Отправка, очистка, команды и
проверки публикации остаются общими.

| Этап | Работа для Flibusta |
| --- | --- |
| Downloading | Потоковое сохранение ответа во внутренний файл и предварительная проверка типа содержимого |
| Preparing | Выделение единственного FB2, проверка XML, извлечение исходного имени и необязательного title |
| Uploading | Общая публикация подготовленного артефакта с исходным именем и snapshot title |
| CleaningUp | Общая очистка своего поколения рабочего каталога после подтверждения публикации |

В артефакте отдельно сохраняется исходное имя. `RelativePath` остается управляемым внутренним путем, как предусмотрено
общим design. Для скачанного ответа добавляется книжный вид артефакта с сохранением числовых значений существующего
enum; готовый FB2 использует существующий `Prepared`. Скачанный и подготовленный файл различаются, поэтому после
ошибки распаковки можно повторить подготовку пригодного входа, а после ошибки S3 — отправку готового FB2.

Неполный или доказанно поврежденный вход не отмечается пригодным артефактом. После ошибки формата ручной повтор
восстанавливает скачивание, а не бесконечно повторяет проверку того же непригодного файла. Оставшиеся байты сохраняются
по общим правилам до повтора или отмены. Повтор публикации сначала согласует прежнее намерение с S3.

### 4. ZIP, XML и исходное имя

Используются стандартные `ZipArchive` и `XmlReader`. MIME служит подсказкой; фактическое содержимое должно быть ZIP
или XML FB2. Для ZIP выбирается ровно один обычный файл с расширением `.fb2` без учета регистра. Другие файлы
не распаковываются, вложенные архивы не обрабатываются, ссылки и неоднозначные архивы не принимаются.

FB2 копируется потоково во внутренний файл, без `ExtractToDirectory` и без использования пути вложения как пути
назначения. Внешнее имя — basename записи ZIP либо `filename*`/`filename` ответа с готовым FB2. Небезопасное имя или
отсутствие имени, позволяющего выполнить требование его сохранения, дают понятную ошибку; выдуманное имя не публикуется
как «исходное». Путь с выходом из каталога отклоняется. Совпадения имен разделяются уникальным префиксом публикации S3,
а не переименованием самого FB2.

XML читается потоково с запрещенными DTD и внешними сущностями. Проверяются корректность XML и принадлежность FB2;
отсутствие необязательных метаданных не становится ошибкой книги. Из `description/title-info` читаются `book-title`
и авторы. Пробельное название становится `null`; при наличии авторов они соединяются через запятую, затем « — Название».
При отсутствии авторов остается название. Файл не пересериализуется, поэтому байты исходного FB2 сохраняются.

Не добавляется новый продуктовый лимит размера книги. Отсутствие полной буферизации, отмена и ограничение распаковки
одним выбранным файлом не отменяют необходимости свободного места на диске. Полная загрузка ZIP/DOM в RAM и
переименование по метаданным не подходят согласованным требованиям.

### 5. Nullable title как данные публикации

`DownloadRecord.Title` уже nullable. Оригинальное имя подготовленного файла передается в проекцию задания отдельно:
книга показывает `title ?? fileName ?? url`, а неизвестные данные остаются `null`. Если общий API еще не предоставляет
имя артефакта, в проекцию добавляется nullable `fileName`.

Публичный DTO библиотеки получает `title: string | null`, сохраняя `name`. UI, включая подписи доступности действий,
использует `title ?? name`. Endpoint содержимого продолжает выбирать исходное имя из собственного ключа/данных файла,
а не из title. Null не заполняется именем на сервере; пустые метаданные нормализуются в null при подготовке.

Предлагается сохранять snapshot title в данных подтвержденной публикации вместе с полным ObjectKey и признаками
объекта `(ETag, Size, LastModified)`. Каталог сначала читает все страницы S3, затем дополняет строки известными
названиями собственных публикаций по полному ключу и совпадающим признакам. Отсутствующие или неизвестные признаки
не разрешают применять прежний title. Ручные и внешние файлы без таких данных получают `title=null`.

Имя и snapshot title включаются в сохраняемое намерение публикации до внешнего действия. После подтверждения S3
записываются признаки объекта и готовность публикации; только такие записи участвуют в дополнении каталога.
Если ответ отправки потерян, общее согласование восстанавливает ту же публикацию и ее сохраненный title.

ETag нужно сохранить во внутреннем результате listing до его преобразования в публичный DTO; SDK S3 предоставляет
его в listing. Получение названий из SQLite выполняется пакетно. Дополнительные HEAD для каждой строки каталога не
требуются; подтверждение публикации остается частью общего протокола S3. Название не служит источником состава каталога.

Альтернатива — S3 metadata с HEAD каждой собственной строки — увеличила бы сетевые обращения каталога. Наложение
по одному basename либо одному ключу без признаков объекта могло бы применить старое название после внешней замены.
Fingerprint обнаруживает обычное изменение объекта, но не дает строгой идентичности версии: замена с теми же
ETag, размером и временем неотличима без дополнительных возможностей хранилища. Обязательное versioning не вводится.

### 6. Проверки и внешние факты

Основные проверки воспроизводимы без живой Flibusta: локальный HTTP-источник с ZIP/FB2/ошибками, файловая SQLite
с миграциями, отдельный MinIO через Testcontainers и React-тесты. Используются актуальные тестовые проекты и команды
`readme.md` после интеграции основного MVP, а не замораживается ранняя структура тестов этой базы.

03.11.2026 без аккаунта проверены [главная](https://flibusta.is/),
[пример карточки FB2](https://flibusta.is/b/441861) и
[метаданные каталога](https://flibusta.is/opds/new/0/new): карточка публикует `/b/{id}/fb2`, каталог объявляет
`application/fb2+zip`. Это подтверждает предлагаемый маршрут, но не заголовки или байты ответа скачивания.
Реальная загрузка и распаковка при подготовке плана не выполнялись. Отдельная проверка при реализации должна
зафиксировать Content-Type, имя/кодировку ZIP, redirects и получение без аккаунта с целевого окружения.

## Risks / Trade-offs

- [Основная очередь и S3 меняются параллельно] → применять поверх принятой реализации их контрактов; не переносить
  в этот change повторную реализацию общих механизмов. Проверки основного сценария yt-dlp остаются обязательными.
- [Источник изменил ответ или требует вход] → проверять фактическое содержимое, завершать попытку с объяснимой ошибкой,
  сохранять диагностику без публикации HTML и без смены согласованного формата.
- [ZIP имеет нестандартную кодировку имени] → подтвердить реальный ответ и воспроизвести его в локальной fixture;
  конкретный способ декодирования не должен менять договоренность об исходном имени.
- [XML/ZIP расходуют ресурсы или содержат внешние ссылки] → потоковая обработка, запрет внешних сущностей,
  распаковка только выбранного файла во внутренний путь и поддержка отмены.
- [Внешняя замена объекта сохраняет весь fingerprint] → полное обнаружение не обещается; для обычного изменения
  признаки из listing сбрасывают наложение старого title без дополнительных запросов на каждый файл.

## Migration Plan

1. Подключать реализацию после готовности общей сохраняемой очереди, публикации и восстановления из параллельного MVP.
   Добавить интеграцию Flibusta в существующие точки выполнения, не запускать этот worktree как готовый продукт.
2. Миграцией сохранить прежние задания и значения enum, добавить идентичность источника, исходное имя артефакта
   и nullable поля snapshot публикации. Для старых публикаций title и неизвестные признаки остаются null.
3. Настроить BaseUrl/AllowedHosts, сделать резервную копию БД, развернуть один экземпляр приложения с прежними volumes.
   Объекты S3 не переименовываются, их содержимое не переписывается ради title.
4. Проверить книгу, null fallback, публичное скачивание с исходным именем, отказ источника и ручной повтор отправки;
   обновить readme и синхронизировать затронутые основные спеки в рамках реализации.
5. При откате использовать совместимый образ и резервную копию БД. Уже опубликованные FB2 сохраняются в S3;
   прежний UI сможет показать исходные имена без новых title. Откат не должен удалять файлы из bucket.
