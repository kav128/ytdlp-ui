# Spec Delta

## MODIFIED Requirements

### Requirement: Контейнер приложения и существующий MinIO

Проект ДОЛЖЕН (SHALL) предоставлять multi-stage Dockerfile одного приложения с .NET runtime, готовым React, yt-dlp и средствами объединения дорожек. Основной сценарий — отдельный контейнер с внешними PostgreSQL и MinIO; Compose с этими сервисами служит вспомогательным локальным вариантом.

#### Scenario: Основное развертывание

- **WHEN** оператор запускает контейнер с настройками внешних PostgreSQL и MinIO
- **THEN** приложение использует заданные сервисы без обязательного запуска новых экземпляров PostgreSQL или MinIO

#### Scenario: Локальный Compose

- **WHEN** оператор использует вспомогательный Compose
- **THEN** приложение может запускаться вместе с локальными PostgreSQL и MinIO

### Requirement: Сохраняемая конфигурация и данные

Приложение ДОЛЖНО (SHALL) хранить временные файлы и ключи защиты серверных сессий в сохраняемых volumes; данные PostgreSQL сохраняются на стороне сервера БД. Строка подключения PostgreSQL, параметры MinIO, OIDC/Authentik, административной группы, учетные данные и пути задаются конфигурацией с переопределением переменными окружения. Команды запуска, HTTPS/reverse proxy и volumes описываются в `readme.md`.

#### Scenario: Замена контейнера

- **WHEN** контейнер заменяется с подключением к прежней PostgreSQL и прежним volumes приложения
- **THEN** БД, очередь, история, промежуточные файлы и ключи защиты сохраняются
- **AND** действующие неотозванные сессии остаются доступны до своего истечения

#### Scenario: Настройки окружения

- **WHEN** оператор переопределяет параметры подключения, OIDC, группу или пути переменными окружения
- **THEN** приложение использует заданные настройки без пересборки фронтенда

#### Scenario: Подключение существующего Authentik

- **WHEN** оператор настраивает OIDC provider/client в существующем Authentik и задает параметры приложения
- **THEN** контейнер использует этот провайдер без установки собственного сервиса идентификации
- **AND** секрет клиента остается только в конфигурации бэкенда

### Requirement: Полный функционал двух архитектур

Приложение ДОЛЖНО (SHALL) обеспечивать полный MVP на `linux/amd64` и `linux/arm64`. Базовые образы, .NET, драйвер PostgreSQL, yt-dlp и FFmpeg должны соответствовать целевой архитектуре; один тег в GHCR содержит общий manifest list обеих платформ.

#### Scenario: Сборка целевых платформ

- **WHEN** Buildx собирает образ для AMD64 и ARM64
- **THEN** каждая платформа получает совместимые runtime-зависимости без копирования чужих нативных бинарных файлов
- **AND** команды целевой архитектуры выполняются подходящим runner или QEMU

#### Scenario: Получение опубликованного тега

- **WHEN** оператор получает один опубликованный тег на AMD64 или ARM64
- **THEN** manifest list выбирает образ соответствующей платформы

### Requirement: CI не запускает приложение и образы

CI ДОЛЖЕН (SHALL) собирать `platforms: linux/amd64,linux/arm64` без запуска приложения и smoke-тестов готовых образов. Работоспособность API, React, подключение к PostgreSQL, yt-dlp и FFmpeg на обеих платформах проверяется отдельно в подходящей среде; сборка не заменяет проверку запуска.

#### Scenario: Проверка pipeline

- **WHEN** выполняется CI
- **THEN** он собирает обе платформы, но не запускает приложение или smoke-тесты образов
- **AND** контейнерные тесты зависимостей через Testcontainers остаются обязательными

#### Scenario: Платформа недоступна локально

- **WHEN** отдельный запуск одной из архитектур проверить невозможно
- **THEN** это ограничение явно указывается без заявления о работоспособности по результату одной сборки
