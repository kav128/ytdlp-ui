# Design

## Context

См. мотивацию в `proposal.md`. Этапы 1–3 реализовали файловую SQLite, EF-миграции и ITicketStore; незакоммиченный этап 4
заменяет DemoStore сохраняемыми командами/запросами. Пользователь выбрал PostgreSQL с чистой БД без импорта. Существующая
модель уже содержит UUID, версии записей, ограничения уникальности и сохраняемые намерения; правила FSM не меняются.

## Goals / Non-Goals

**Goals:** единый PostgreSQL provider для production и интеграционных проверок; прежний контракт SSO и HTTP;
атомарные команды и claim очереди, независимые от SQLite-specific API; воспроизводимый локальный запуск.

**Non-Goals:** импорт SQLite, перенос прежних tickets, несколько одновременно работающих экземпляров приложения,
распределенная очередь, высокая доступность СУБД и управление внешним сервером PostgreSQL.

## Decisions

1. EF Core 10 использует Npgsql 10 через CPM. Создается начальная миграция PostgreSQL; старые SQLite-миграции и
   interceptor исключаются из действующего приложения. SQLite-файлы автоматически не открываются и не удаляются.
   Совместный выбор двух провайдеров и синхронизация двух БД не нужны для согласованного чистого старта.
2. Сохраняются UUID и явный optimistic `Version`; уникальные ограничения защищают нормализованный URL и активную
   попытку. Ошибки PostgreSQL различаются по SQLSTATE, без разбора локализованного текста исключения. Внешний S3 I/O
   выполняется вне транзакции с повторной проверкой версии перед сохранением перехода.
   Для длинного URL индексируется 32-байтный SHA-256 нормализованной строки UTF-8, а полная строка остается `text`:
   [B-tree ограничивает размер записи индекса](https://www.postgresql.org/docs/current/btree.html), поэтому прямой
   unique index на неограниченном URL несовместим с принимаемым длинным вводом. Hash вычисляется централизованно при
   сохранении; поиск дополнительно сравнивает полную строку. Совпадение hash разных строк дает технический конфликт,
   без объединения заданий или выдачи чужого ID. Используется BCL, дополнительное расширение PostgreSQL не нужно.
3. Даты хранятся как `timestamp with time zone` в UTC, без SQLite-конвертера миллисекунд. Server ticket store получает
   нейтральное имя; protected tickets, срок 12 часов и отзыв до успешного ответа сохраняются.
4. Claim очереди выполняется короткой транзакцией PostgreSQL с общим guard и проверкой отсутствия исполняемой попытки;
   блокировка только выбранной строки с `SKIP LOCKED` сама по себе не обеспечивает правило одного исполняемого задания.
   Сортировка использует QueuedAt и стабильный tie-breaker. Обработка и медиапроцессы остаются этапами 5–6.
5. NUnit SetupGlobal владеет PostgreSQL Testcontainer, а SetupBase/тестовая фабрика — изолированной БД сценария и
   временными файлами. Перезапуск внутри теста сохраняет ту же БД и ключи. Миграции и constraints проверяются на
   PostgreSQL. MinIO имеет собственный контейнер для Storage-сценариев; пользовательские БД/bucket не используются.
   Все HTTP-тесты с настоящим хранилищем сессий теперь требуют Docker; unit-тесты остаются без Docker.
6. Основной запуск подключается к внешнему серверу через `ConnectionStrings__AppDatabase`; локальный Compose может
   запускать готовый PostgreSQL. При недоступной БД запуск не включает fallback. В контейнере приложения остаются
   volumes ключей и рабочих файлов, а не сервер PostgreSQL.

Технический default для тестов/локального Compose — поддерживаемая стабильная PostgreSQL 18.6 и готовый multiarch image;
это не ограничивает оператора единственным minor. Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3 согласуется с EF 10.
Версии проверены по [политике PostgreSQL](https://www.postgresql.org/support/versioning/) и
[официальному NuGet](https://www.nuget.org/packages/Npgsql.EntityFrameworkCore.PostgreSQL/10.0.3).

## Risks / Trade-offs

- [Внешняя зависимость БД] → понятная проверка конфигурации и ошибка startup/migration без вывода пароля; документация
  настройки и резервного копирования PostgreSQL.
- [Отличия SQL и ограничений] → настоящие migrations/constraints/concurrency тесты, UTC round-trip и restart сессии.
- [Старые cookie после переключения] → tickets не импортируются, требуется новый SSO-вход; S3-файлы не затрагиваются.
- [Цена интеграционных тестов] → один контейнер набора, изолированные БД сценариев и явное освобождение; отсутствие
  Docker является ошибкой интеграционного запуска.

## Migration Plan

1. Подготовить новую PostgreSQL и учетную запись приложения, остановить прежний экземпляр.
2. Сохранить прежний SQLite-файл как резервную копию, задать новую строку подключения и прежние S3/volumes ключей и
   рабочих файлов. Приложение применит начальную PostgreSQL-миграцию; история начнется заново.
3. Проверить новый SSO-вход, отзыв/restart, библиотеку, постановку и конкурентные команды. Проверки worker добавляются
   в последующих этапах полного MVP.
4. Для отката вернуть прежний образ и прежний SQLite-файл; новые PostgreSQL-данные обратно не переносятся автоматически.
   Никакой автоматической очистки S3 при переходе или откате нет.

Общий design/readme и активный auth delta обновляются при реализации. При итоговой синхронизации сначала применяется
auth delta, затем PostgreSQL delta; исторические результаты этапов 1–3 не переписываются.

При планировании технический идентификатор сценария «Проверка SQLite» сохранялся в delta, поскольку валидатор запрещает
терять сценарий при MODIFIED. После реализации и синхронизации он переименован в «Проверка сохранения данных» в основной
спеке и delta одновременно, без изменения шагов и потери сценария.
