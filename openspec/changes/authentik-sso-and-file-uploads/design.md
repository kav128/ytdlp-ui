# Design

## Context

Причины и границы изменения описаны в [proposal.md](proposal.md). Контракт находится в delta
specs [administrator-access](specs/administrator-access/spec.md), [file-uploads](specs/file-uploads/spec.md), [public-library](specs/public-library/spec.md), [web-interface](specs/web-interface/spec.md)
и [container-delivery](specs/container-delivery/spec.md).

Наблюдаемое состояние перед началом реализации (историческая база change):

- `Features/Auth/AuthEndpoints` принимает пароль, выдает собственные токены, предоставляет refresh и logout.
  `AuthenticationServiceCollectionExtensions` настраивает JWT Bearer и политику `Admin`.
- `AdminSessionRecord` в SQLite содержит даты сессии/отзыва и хеш refresh token. `TestApplicationFactory` использует
  временную файловую БД и ephemeral Data Protection.
- React `useAuth` хранит пару в `sessionStorage`, выполняет refresh и защищает новую сессию от поздних ответов прежней.
  API-клиент умеет JSON и Bearer, но не отправку файлов.
- `LibraryEndpoints` читает демонстрационные файлы из `DemoStore` и возвращает `text/plain`. `Infrastructure/Storage`
  пока не реализован; AWS SDK и отдельного проекта интеграционных тестов MinIO нет.
- Схема уже содержит `StorageTransferRecord.ObjectKey`, связь публикации с заданием и доменный автомат `Download`.
  Реальный worker и постоянный API заданий по URL относятся к последующим этапам базового MVP.

Общий [технический проект](../../design.md), особенно разделы 7, 9–11, обновляется вместе с реализацией. Этап OIDC уже
заменяет прежнюю авторизацию; интеграция S3/ручных файлов выполняется далее, поэтому фактический статус отмечается
отдельно.

## Goals / Non-Goals

**Goals:**

- Использовать существующие Minimal API, React и SQLite без нового сервиса сессий или отдельного приложения авторизации.
- Проверять права на сервере и хранить чувствительные данные OIDC на стороне бэкенда.
- Подключить реальный S3-каталог и потоковую передачу так, чтобы произвольные файлы работали независимо от будущего
  worker yt-dlp.
- Сохранить данные, историю и guards существующего домена загрузок.

**Non-Goals:**

- Реализация оставшихся этапов скачивания по URL, универсальной системы ролей, OAuth-сервера или отдельного
  frontend-сервера.
- Получение refresh token Authentik для вызовов сторонних API, глобальный SSO logout и прием уведомлений back-channel
  logout в этом изменении.
- Собственная очередь ручных отправок, их пользовательская история, побайтовое возобновление, массовая отправка и
  редактирование файлов.

## Decisions

### 1. OIDC выполняет бэкенд

Пользователь согласовал Authentik, права по заданной группе и HttpOnly cookie. Выбирается confidential client с
Authorization Code и PKCE через стандартный `Microsoft.AspNetCore.Authentication.OpenIdConnect`; это техническая
реализация согласованного направления. Middleware проверяет state, nonce, подпись, issuer, audience, срок и correlation
начатого входа. Discovery/JWKS читаются по HTTPS, допустимые алгоритмы берутся из настроенного провайдера и не
ослабляются для обхода проверки.

Основание выбора code flow и серверной
обработки — [официальная документация ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-oidc-web-authentication?view=aspnetcore-10.0).
Authentik поддерживает этот flow, PKCE, discovery и передачу групп через scope
mappings: [OAuth 2.0 provider](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/).

Настройки: `Oidc:Authority`, `ClientId`, `ClientSecret`, `GroupsClaim` и `AdminGroup`. Authority задается как issuer
конкретного приложения Authentik; для MVP используется стандартный per-provider issuer. Callback фиксирован
`/signin-oidc`; в Authentik регистрируется точный внешний HTTPS URI. Scopes — `openid` и `profile`; mapping настроенного
claim должен передавать группы. Выдача OIDC-токенов собственному фронтенду и `offline_access` не нужны,
`SaveTokens=false`.

После проверки ответа middleware сопоставляет настроенную группу с проверенными claims. Пустая конфигурация, отсутствие
claim или несовпадение группы закрывают доступ. Несколько участников группы могут быть администраторами. Идентичность
задается парой issuer/sub, а не изменяемыми email или отображаемым именем. При SSO пользователя без группы callback
возвращает браузер на локальный `/?authError=access_denied` без создания административной сессии. UI показывает
локализованный отказ и публичный каталог. Общая ошибка использует только фиксированный login_failed; данные провайдера и
исключений в query не передаются. Административные API сохраняют 401/403 JSON без redirect.

Рассмотренные альтернативы: SPA с Bearer в `sessionStorage` отклонена пользователем в пользу cookie; собственная выдача
JWT после Authentik создала бы лишний механизм токенов; proxy-auth не соответствует выбранному OIDC.

### 2. Сохраняемая серверная сессия в SQLite

Использовать Cookie Authentication с `ITicketStore` на существующей SQLite. Cookie содержит защищенную ссылку на
серверный ticket; сохраненный ticket содержит минимальные проверенные identity/group claims, без access/refresh tokens.
Для операций ticket store создается короткий DI scope с `AppDbContext`; долгоживущий DbContext не добавляется.

Новая EF-миграция заменяет структуру локальных сессий полями issuer/sub и защищенным сериализованным ticket, сохраняя
ID, даты истечения и отзыва. Старые сессии отзываются; старый refresh hash удаляется. Ранее примененные миграции не
переписываются. Выдача cookie происходит только после успешной записи ticket. Получение ticket проверяет его наличие,
отзыв и абсолютное истечение без кеша, переживающего отзыв.

Абсолютный срок остается 12 часов от входа, `SlidingExpiration=false`; cookie не постоянная. В production используются
`HttpOnly`, `Secure`, host-only область и `SameSite=Lax` для основной cookie; correlation/nonce cookies настраиваются
middleware под выбранный OIDC response mode. Callback обрабатывает middleware. Cookie действует между вкладками одного
браузера, что заменяет прежнюю изоляцию `sessionStorage`.

Data Protection использует постоянный каталог `Paths:DataProtectionKeysDirectory`, в контейнере `/data/keys`, и
стабильное application name. Каталог доступен только пользователю приложения и сохраняется вместе с `/data`. Это
необходимо для cookie после замены контейнера:
см. [хранение ключей в Docker](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/default-settings?view=aspnetcore-10.0).
Тесты восстановления используют временный сохраняемый key ring вместо ephemeral provider; остальные тесты сохраняют
изоляцию.

Выход отзывает ticket в SQLite и удаляет cookie только приложения. Сессия Authentik и другие приложения не завершаются.
В другой вкладке отзыв обнаружится при следующей проверке API; немедленная синхронизация вкладок отдельным механизмом не
добавляется. Ошибка БД не изображается успешным отзывом. После перезапуска действующая сессия работает при сохранении БД
и ключей; прежние локальные JWT не принимаются.

Альтернативы: только зашифрованная cookie без серверного ticket не обеспечивает немедленный сохраняемый отзыв; новый
Redis не нужен при имеющейся SQLite; сохранение собственных refresh tokens не требуется без downstream API.

### 3. Команды с cookie защищаются от CSRF

`GET /api/auth/csrf` возвращает request token после проверки административной сессии; React держит его в памяти и
передает в `X-CSRF-TOKEN` для POST/DELETE и других изменяющих команд. Все существующие административные endpoints
получают эту проверку вместе с политикой `Admin`. Вход OIDC защищается протокольными state/nonce/correlation, а не
произвольным отключением проверок callback.

CSRF проверяется до чтения тела отправляемого файла и внешних действий. SameSite используется дополнительно. API
сохраняет same-origin модель, CORS не включается. `401` означает отсутствие сессии, `403` — отсутствие прав,
`400 antiforgery_failed` — неверное CSRF-подтверждение; эти ошибки не подменяются HTML-redirect. Auth-ответы имеют
`Cache-Control: no-store`.

React при загрузке и возвращении на вкладку запрашивает `/api/auth/session`. `401` защищенного запроса очищает
административное состояние; сетевой сбой не считается успешным logout. Поздние ответы проверяются относительно
актуальной UI-сессии, как и сейчас. При миграции удаляется прежний `ytdlp-ui.session`, тип AccessToken, refresh-код и
заголовок Bearer.

### 4. Контракт API

| Метод и маршрут                     | Доступ / защита                  | Результат                                                                                                                            |
|-------------------------------------|----------------------------------|--------------------------------------------------------------------------------------------------------------------------------------|
| `GET /api/auth/login?returnUrl=/`   | Навигация браузера               | Начало OIDC challenge; принимается только локальный returnUrl                                                                        |
| `/signin-oidc`                      | Протокольный callback middleware | Проверка ответа и группы, создание ticket, возврат в библиотеку; ошибка не создает сессию                                            |
| `GET /api/auth/session`             | Публичный, cookie опциональна    | `200 { authenticated, sessionId }`; без сессии false/null, sessionId — независимый ID UI, а не credential или ключ ticket            |
| `GET /api/auth/csrf`                | Admin, cookie                    | `200 { requestToken }`, без кеширования                                                                                              |
| `POST /api/auth/logout`             | Admin, cookie + CSRF             | `204` после отзыва текущего ticket                                                                                                   |
| `POST /api/library/uploads`         | Admin, cookie + CSRF             | `multipart/form-data`, ровно одна file-part `file`; `201` с прежним LibraryFile DTO и Location на content URL после подтверждения S3 |
| `GET /api/library`                  | Публичный                        | Полный список S3 в прежнем формате DTO                                                                                               |
| `GET /api/library/{fileId}/content` | Публичный                        | Поток с attachment; `404` для отсутствующего объекта                                                                                 |
| `DELETE /api/library/{fileId}`      | Admin, cookie + CSRF             | `204` после подтвержденного удаления, включая уже отсутствующий объект; guards связанных заданий сохраняются                         |

Прежние `POST /api/auth/login` и `POST /api/auth/refresh` удаляются; они не остаются запасным способом входа.
Неизвестный API-маршрут возвращает `404`, а не React HTML. Управление заданиями сохраняет маршруты и доменные правила,
получая cookie/CSRF вместо Bearer.

Ошибки отправки: `400 invalid_upload` — нет file-part, частей больше одной или форма повреждена; `401/403` — доступ;
`400 antiforgery_failed` — CSRF; `503 storage_unavailable` — недоступность S3; прочие ошибки используют существующий
формат Problem Details с локализуемым code. Технический `413` от настроенного reverse proxy или сервера документируется
отдельно, без объявления нового продуктового лимита.

### 5. Реальная библиотека S3 и ручная отправка

Добавить `ObjectStorage` на официальном `AWSSDK.S3` с настройками endpoint/bucket/region/credentials/path-style и
небольшой сервис библиотеки. `LibraryFile` переносится из пространства имен моков в контракт библиотеки. Реальный
listing обрабатывает все continuation pages; `fileId` — обратимое Base64url-представление полного UTF-8 ключа. Исходное
имя внешних объектов выводится из ключа, ручных отправок — из безопасного имени в сгенерированном ключе. SQLite не
определяет состав каталога.

`POST /uploads` вручную читает multipart последовательно без буферизующего `IFormFile`. Метод
соответствует [рекомендациям по потоковым отправкам ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/mvc/models/file-uploads?view=aspnetcore-10.0).
Проверка прав и CSRF выполняется до чтения. Проверяется ровно одна file-part; разобранные части не передаются shell,
инструментам медиа или статическому серверу. Серверные лимиты тела на этом endpoint и ограничения reverse proxy
согласуются с потоковым режимом; небольшие технические пределы заголовков и метаданных остаются.

Предлагаемый ключ — `uploads/<upload-id>/<safe-name>`. Генерируется независимый UUID; имя очищается от разделителей пути
и управляющих символов, а UTF-8 имя сохраняется для отображения и attachment. Совпадающие имена получают разные ключи.
Расширение и MIME не ограничивают допустимые типы; пустой файл отправляется как пустой объект. Нет overwrite по одному
лишь имени.

Содержимое читается ограниченными буферами и отправляется через S3 multipart с учетом технических пределов провайдера и
размеров частей. В память не загружается весь файл. Проверяются завершение запроса, размер и собственный объект; только
после проверки формируется `201`. При неопределенном исходе Complete сначала выполняется HEAD собственного уникального
ключа с проверкой metadata/размера. Наличие объекта не доказывается одним совпадением имени.

Реализация хранит одну часть на диске в `/data/work/uploads/<operation-id>/part`, RAM-буфер 128KiB. По известному
Content-Length рассчитывается размер части для 10000 частей в границах 5MiB–5GiB; неизвестная длина использует 5GiB-части
и требует соответствующего временного диска. SDK не повторяет Initiate/Complete автоматически; неизвестный Initiate
согласуется listing multipart по точному уникальному ключу. Все части формы проверяются до Complete. Технические
пределы транспорта, proxy, диска и провайдера документируются в readme без нового продуктового лимита файла.

Обычная ошибка или отключение клиента отменяют ввод-вывод и прерывают известный multipart upload в finally; cleanup
использует отдельный ограниченный токен, а не уже отмененный RequestAborted. Полностью опубликованный объект остается
обычным файлом библиотеки даже при потере ответа браузеру; повторная отправка создаст новый объект, автоматическое
восстановление такой операции не обещается. Незавершенные части не становятся элементом каталога. Журнал ручных отправок
и продолжение после рестарта не добавляются.

Чтение S3 передается непосредственно в HTTP response, response/stream освобождаются после завершения или отключения
клиента. Используются `Content-Disposition: attachment`, безопасное имя, Content-Length и `nosniff`; неизвестный тип —
`application/octet-stream`. После начала потока ошибка не дописывается JSON в файл. Range-поддержка остается за
пределами этого изменения.

Ручная отправка не получает `DownloadRecord` и не занимает очередь yt-dlp. Для удаления связанного результата сервис
находит публикацию по сохраненному ключу, применяет существующий агрегат и guards, сохраняет намерение до S3 и результат
после подтверждения; очистка в `CleaningUp` по-прежнему запрещает удаление. Объекты без связанного задания удаляются
напрямую через библиотеку. Несовпадение идентичности собственной публикации под прежним ключом дает конфликт.

Альтернативы: прямой presigned upload потребовал бы отдельного контракта/CORS и выдачи браузеру адреса MinIO;
буферизация целого файла не подходит произвольным размерам; fake download с выдуманным URL нарушил бы смысл заданий и их
повтора.

### 6. UI и эксплуатация

Кнопка входа остается справа сверху и начинает навигацию на `/api/auth/login`. Формы пароля нет. После возврата UI
проверяет session и получает CSRF перед командами. В каталоге администратора есть отдельная кнопка «Загрузить файл»;
URL-форма остается в блоке заданий. Нативный file picker не ограничивается медиа через accept. Показываются имя и
состояние «отправляется / подтверждается / готово / ошибка» без выдуманного процента. Повторное нажатие во время запроса
блокируется; после успеха каталог перечитывается. Проверки актуальности сессии не позволяют ответу старого входа закрыть
новый диалог.

Формы и сообщения добавляются в ресурсы EN/RU и работают на телефоне и десктопе. Ручная отправка использует FormData без
JSON.stringify и без ручного задания multipart boundary. Данные не отправляются на сторонние origin.

В readme описываются `Oidc__Authority`, `Oidc__ClientId`, `Oidc__ClientSecret`, `Oidc__GroupsClaim`, `Oidc__AdminGroup`,
`Paths__DataProtectionKeysDirectory`, `Paths__WorkDirectory`, настройки S3 и volume `/data`. HTTPS может завершаться на существующем
reverse proxy; Forwarded Headers принимаются только от настроенных доверенных proxy, чтобы callback использовал
правильный внешний адрес. Конфигурация группы и секреты находятся на сервере; публичные ошибки не раскрывают внутренние
значения.

### 7. Проверки

- OIDC: изолированный тестовый issuer с discovery/JWKS и подписанными ответами, callback/state/nonce/PKCE, неверные
  подпись/issuer/audience/срок, отсутствие группы, отсутствие локального fallback. Тест не обращается к
  пользовательскому Authentik.
- SQLite/API: новая миграция поверх существующей БД без потери заданий, сохранение/истечение/отзыв ticket, рестарт с
  прежними ключами, отказ БД и конфигурации. Использовать FakeTimeProvider, не ожидание реальных 12 часов.
- API: публичные GET без входа, все защищенные POST/DELETE с cookie и CSRF, отсутствие redirect для `401`, отклонение
  прежних JWT/refresh, неподходящий returnUrl.
- MinIO через Testcontainers: разные типы и нулевой файл, одинаковые и сложные имена, полный listing включая внешний
  объект, целостность байтов, потоки больше буфера, отмена и ошибки multipart, потеря ответа Complete, удаление и guards
  связанных заданий.
- React: SSO-навигация, проверка session, отсутствие browser tokens/refresh, формы отправки, двойной клик, ошибки и
  поздние ответы, EN/RU и доступность на мобильном экране.
- Сборка/поставка: frontend build, .NET build/publish и UI в публикации, интеграционные тесты с Docker в CI, отдельно
  доступные проверки запуска двух архитектур. CI не запускает production-приложение и smoke-тесты образов.

## Risks / Trade-offs

- [Группа меняется после входа] → claims фиксируются на момент SSO; локальная сессия ограничена 12 часами. Мгновенный
  отзыв через Authentik/back-channel не заявляется; logout приложения немедленно отзывает его ticket.
- [Сбой процесса во время ручного multipart] → частичный объект не появляется в каталоге; при обычных ошибках upload
  abort выполняется. После жесткого завершения процесса возможны оставшиеся части в S3; их операторская очистка не равна
  готовому файлу и не дает автоматического повтора задания.
- [Потерян ответ успешной отправки] → каталог S3 остается источником истины; UI может перечитать его. Повторный выбор
  файла — новая отправка с новым ключом, без обещания дедупликации ручных файлов.
- [Неверные issuer, mapping или reverse proxy] → документировать точные параметры и проверять их в отдельном smoke с
  существующим Authentik; не отключать проверки протокола ради входа.
- [Технический лимит тела на proxy] → документировать фактическую настройку и проверять файл больше стандартного
  серверного лимита; не принимать небольшой framework default за согласованный лимит продукта.

## Migration Plan

1. Реализовать и проверить изменение с изолированными OIDC и MinIO. Новая миграция сохраняет задания/историю, отзывает
   старые локальные сессии и создает схему server tickets; frontend удаляет прежние токены из sessionStorage.
2. До развертывания настроить в существующем Authentik confidential provider/client, точный HTTPS redirect URI и выдачу
   настроенной группы; фактические Authority, ClientId, ClientSecret, имя claim и группы задаются оператором.
3. Сделать резервную копию SQLite, остановить прежний экземпляр контейнера, подключить прежние данные и постоянные ключи
   `/data/keys`, задать OIDC/Storage и запустить новый экземпляр. Все администраторы входят заново через SSO.
4. Отдельно проверить доступ участника группы, отказ постороннему, локальный logout и отправку/публичное скачивание
   тестового файла. Отдельно фиксировать, какая архитектура реально проверена.
5. При откате вернуть согласованную резервную копию SQLite и прежний образ, а не запускать его на новой схеме. Уже
   опубликованные S3-файлы сохраняются; автоматическое их удаление при откате не выполняется.

При завершении изменения обновить общий `openspec/design.md`, карту capabilities, `AGENTS.md` ссылкой на `file-uploads`
и readme. При синхронизации основных спек обновить устаревший Purpose `administrator-access`, описывающий единственного
администратора и refresh, на фактический OIDC-контракт.

Реализация уточняет проверку подписи: .NET10.0.12 в code flow выставляет RequireSignedTokens=false; дополнительный guard
OnTokenValidated запрещает пустую подпись/alg=none.
См. [официальный handler](https://github.com/dotnet/aspnetcore/blob/v10.0.12/src/Security/Authentication/OpenIdConnect/src/OpenIdConnectHandler.cs#L755-L757).
Остальные криптографические/протокольные проверки сохраняются. Неиспользуемые remote-signout endpoints отключены. Поле
sessionId отдельное от server ticket key, стабильно в пределах входа, меняется при новом SSO и не принимается как
credential. Trusted Forwarded Headers настраиваются ReverseProxy:KnownProxies/KnownNetworks/AllowedHosts; при пустом
наборе доверенных адресов обработка заголовков отключена.
