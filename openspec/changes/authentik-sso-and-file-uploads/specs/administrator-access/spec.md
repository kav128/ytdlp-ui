# Spec Delta

## MODIFIED Requirements

### Requirement: Публичное чтение и защищенное управление

Сервер ДОЛЖЕН (SHALL) разрешать анонимное чтение каталога и скачивание файлов и требовать действительную административную сессию для создания заданий, чтения их состояний и истории, повтора, отмены, отправки локальных файлов и удаления файлов.

#### Scenario: Анонимный посетитель читает библиотеку

- **WHEN** посетитель без входа запрашивает каталог или существующий файл
- **THEN** сервер предоставляет публичные данные или файл без входа

#### Scenario: Административный запрос без входа

- **WHEN** запрос управления или чтения заданий не содержит действительной административной сессии
- **THEN** сервер отклоняет запрос независимо от видимости элементов интерфейса
- **AND** данные заданий не передаются посетителю

### Requirement: Выход и отзыв сессии

Сервер ДОЛЖЕН (SHALL) при успешном выходе сохранять отзыв текущей сессии в PostgreSQL и удалять ее cookie. Клиент очищает административные данные после выхода или `401`. Выход действует в приложении, не завершает SSO в других приложениях и не отменяет фоновые задания.

#### Scenario: Успешный выход

- **WHEN** администратор выходит из текущей сессии
- **THEN** сервер отзывает сессию, и прежняя cookie больше не принимается, в том числе после рестарта
- **AND** клиент очищает закрытые данные
- **AND** фоновые задания продолжаются

#### Scenario: Окончательный отказ в авторизации

- **WHEN** защищенный запрос получает `401` из-за истекшей или недействительной сессии
- **THEN** клиент очищает административные данные и прекращает их опрос

#### Scenario: Поздний ответ прежней сессии

- **WHEN** ответ прежнего входа приходит после выхода или нового входа
- **THEN** ответ не восстанавливает старую сессию и не изменяет данные новой

#### Scenario: Ошибка отзыва

- **WHEN** запись отзыва в БД не удалась
- **THEN** сервер не подтверждает успешный отзыв

#### Scenario: Сессия Authentik после выхода

- **WHEN** пользователь вышел из приложения при действующей SSO-сессии Authentik
- **THEN** другие приложения Authentik продолжают работать
- **AND** новый вход в это приложение может использовать существующую SSO-сессию

## ADDED Requirements

### Requirement: Вход через Authentik по OIDC

Приложение ДОЛЖНО (SHALL) аутентифицировать администратора через настроенный Authentik по OIDC с проверкой ответа провайдера. Форма логина/пароля и выдача собственных access/refresh tokens удаляются; сбой SSO не включает запасной локальный вход.

#### Scenario: Успешный SSO

- **WHEN** пользователь запускает вход и Authentik успешно подтверждает его идентичность
- **THEN** приложение проверяет ответ OIDC и права, создает локальную сессию и возвращает пользователя в библиотеку
- **AND** пароль не вводится и не обрабатывается приложением

#### Scenario: Отмена или недействительный ответ

- **WHEN** вход отменен или ответ имеет неверную подпись, issuer, audience, срок либо не соответствует начатому входу
- **THEN** локальная административная сессия не создается

#### Scenario: Прежние локальные токены

- **WHEN** клиент предъявляет JWT или refresh token прежней локальной авторизации
- **THEN** токены не предоставляют административный доступ и не продлевают сессию

### Requirement: Права администратора по группе Authentik

Сервер ДОЛЖЕН (SHALL) выдавать административные права только участникам заданной в конфигурации группы из проверенных данных Authentik. Имя группы и claim ее передачи настраиваются; отсутствующий claim, пустая группа или отсутствие членства не дают прав.

#### Scenario: Участник группы

- **WHEN** проверенная идентичность Authentik содержит настроенную административную группу
- **THEN** приложение разрешает административную сессию

#### Scenario: Пользователь без группы

- **WHEN** Authentik подтвердил пользователя, но требуемой группы в проверенных данных нет
- **THEN** административный вход отклоняется с отказом доступа
- **AND** публичный каталог остается доступным

#### Scenario: Группа в непроверенном запросе

- **WHEN** клиент подставляет название группы в параметрах запроса или неподтвержденных данных
- **THEN** эти данные не предоставляют административных прав

### Requirement: Серверная сессия браузера

Приложение ДОЛЖНО (SHALL) хранить сессию на сервере и использовать защищенную HttpOnly cookie для запросов собственного API. В production cookie передается только по HTTPS. Токены OIDC и client secret не доступны JavaScript, не попадают в `sessionStorage`, `localStorage`, ссылки скачивания или логи.

#### Scenario: Запрос после входа

- **WHEN** клиент обращается к собственному API с действующей cookie
- **THEN** сервер восстанавливает сессию без Bearer-токена в браузерном коде

#### Scenario: Несколько вкладок

- **WHEN** другая вкладка того же браузера обращается к приложению с общей действующей cookie
- **THEN** она использует ту же серверную сессию после проверки через API

### Requirement: Абсолютный срок серверной сессии

Сервер ДОЛЖЕН (SHALL) ограничивать локальную сессию 12 часами от успешного входа без продления от активности. После истечения требуется новый OIDC-вход, который может использовать действующую SSO-сессию Authentik.

#### Scenario: Активность в пределах срока

- **WHEN** пользователь выполняет запросы в течение локальной сессии
- **THEN** абсолютное время ее истечения не сдвигается

#### Scenario: Истечение срока

- **WHEN** прошло 12 часов от входа
- **THEN** cookie перестает предоставлять административные права
- **AND** для восстановления доступа запускается SSO

### Requirement: Проверка и сохранение серверной сессии

Приложение ДОЛЖНО (SHALL) проверять действительность сессии через API до загрузки административных данных и сохранять действующие сессии при перезапуске с прежними БД и ключами защиты. Отозванная, отсутствующая или истекшая сессия не принимается.

#### Scenario: Загрузка страницы

- **WHEN** страница открывается или перезагружается
- **THEN** UI проверяет сессию на бэкенде до получения закрытых данных

#### Scenario: Перезапуск

- **WHEN** приложение перезапускается с прежними БД и ключами защиты
- **THEN** действующая сессия остается доступной, а отзыв сохраняет силу

#### Scenario: Ошибка сохранения

- **WHEN** создать серверную сессию в БД не удалось
- **THEN** вход не подтверждается и действующая cookie не выдается

### Requirement: Защита команд от CSRF

Сервер ДОЛЖЕН (SHALL) проверять CSRF-защиту всех изменяющих команд, авторизуемых cookie, включая выход, управление заданиями, отправку и удаление файлов. API возвращает ошибки авторизации без перенаправления на HTML-страницу входа.

#### Scenario: Поддельная команда

- **WHEN** изменяющий запрос имеет cookie, но не имеет действительного CSRF-подтверждения
- **THEN** сервер отклоняет его до побочных действий

#### Scenario: Потерянная сессия API

- **WHEN** административный API вызывается без действующей сессии
- **THEN** он возвращает `401`, а не перенаправление в Authentik

### Requirement: Конфигурация провайдера без секретов на клиенте

Приложение ДОЛЖНО (SHALL) получать OIDC-параметры и настройки административной группы из конфигурации бэкенда и отклонять запуск при отсутствующих обязательных значениях. Client secret и учетные данные S3 не выводятся в интерфейс, диагностику и логи; примеры используют демонстрационные значения.

#### Scenario: Неполная конфигурация

- **WHEN** обязательные параметры OIDC или административной группы не заданы
- **THEN** запуск завершается понятной ошибкой без раскрытия секретов

## REMOVED Requirements

### Requirement: Единственный администратор из конфигурации

**Reason**: Учетные записи и принадлежность к административной группе управляются в Authentik.
**Migration**: Удалить локальный пароль и вход по нему; разрешать SSO участникам настроенной группы.

### Requirement: Bearer JWT собственного API

**Reason**: Пользователь выбрал серверную сессию с HttpOnly cookie.
**Migration**: Удалить собственные JWT и передачу Authorization из React; административные команды используют cookie и CSRF-защиту.

### Requirement: Проверка ключа подписи при запуске

**Reason**: Приложение перестает подписывать собственные HS256 JWT.
**Migration**: Удалить Jwt:SigningKey; проверять настроенный OIDC issuer и сохранять ключи защиты серверной сессии.

### Requirement: Сроки access token и сессии

**Reason**: Собственные access tokens на 5 минут больше не выдаются.
**Migration**: Сохранить абсолютный срок локальной cookie-сессии 12 часов отдельным требованием; сроки токенов OIDC определяет Authentik.

### Requirement: Сохраняемые сессии и ротация refresh token

**Reason**: Приложению не требуется выдача и ротация своих refresh tokens.
**Migration**: Удалить публичный refresh API и прежние локальные токены; PostgreSQL хранит серверные сессии и отзыв.

### Requirement: Сессия вкладки браузера

**Reason**: Cookie-сессия браузера заменяет токены отдельной вкладки в sessionStorage.
**Migration**: Очистить прежние токены при обновлении UI, проверять серверную сессию и учитывать общую cookie нескольких вкладок.
