# Инструкции для работы над yt-dlp WebUI

## Контекст и требования

- Перед изменениями прочитай `MVP-SPEC.md` в корне репозитория: это основное ТЗ проекта.
- При проектировании и реализации также учитывай `TECHNICAL-DESIGN.md`: он содержит предлагаемые решения и открытые вопросы. Не считай нерешенные вопросы и технические defaults согласованными изменениями требований.
- Учитывай актуальные указания пользователя. При согласованном изменении требований обновляй ТЗ вместе с реализацией.
- Общайся с пользователем и веди документацию на русском языке. Для идентификаторов в коде используй английский.
- Приватные поля именуй в формате `_camelCase`, включая `static` и `readonly`: например, `_snapshot`, `_downloadId`.
- Сохраняй изменения пользователя и не затрагивай файлы, не относящиеся к задаче.
- Выбирай простые решения в пределах MVP. Не добавляй новые функции и инфраструктуру без необходимости для текущей задачи.

## Архитектура

- ASP.NET Core 10.0 Web API и React составляют одно приложение с раздельными каталогами исходников и сборками. Kestrel раздает API и собранный UI.
- Реализуй HTTP API через Minimal API. Группируй endpoints по функциональным областям в `Features/`, а в `Program.cs` вызывай методы их регистрации. Обработчики отвечают за HTTP-контракт и вызывают сервисы; бизнес-логику и управление фоновыми заданиями держи в соответствующих компонентах.
- По умолчанию React и .NET собираются отдельно, включая CI и Dockerfile. Совместная сборка через `dotnet build` доступна явно по флагу `-p:BuildFrontend=true` или target `BuildFrontend`. Публикация включает готовый фронтенд в `wwwroot`.
- Храни задания, состояния этапов и историю попыток в SQLite через Entity Framework Core. Изменения схемы оформляй миграциями.
- Для взаимодействия с MinIO используй официальный пакет `AWSSDK.S3`.
- Выполняй длительные загрузки в фоновом обработчике. HTTP-запрос постановки задания не должен ждать окончания загрузки.
- Не вводи дополнительные сервисы очередей или БД для MVP.

## Структура репозитория и сборка

- Соблюдай целевую структуру из `MVP-SPEC.md`: корневое решение `Ytdlp.Ui.slnx`, production-код в `src/`, тестовые проекты в `tests/`, GitHub Actions в `.github/workflows/`.
- Размещай React в `src/Ytdlp.Ui.Client/`, бэкенд — в `src/Ytdlp.Ui/`; сохраняй один Web-проект, единый контейнер приложения и отдельные тестовые проекты. Результат сборки React хранится в `src/Ytdlp.Ui.Client/dist/` и не коммитится.
- Добавляй новые production- и тестовые проекты в корневое `.slnx`-решение.
- Фиксируй .NET SDK в `global.json` и согласуй его с CI и Docker. Тип SDK (`Microsoft.NET.Sdk.Web` или `Microsoft.NET.Sdk`) задавай в `.csproj`.
- Выноси общие свойства компиляции в корневой `Directory.Build.props`: `TargetFramework=net10.0`, явный `LangVersion`, `Nullable=enable`, `ImplicitUsings` и другие общие настройки. Не используй `latest` или `preview` для версии языка.
- Настройки production- и тестовых проектов размещай соответственно в `src/Directory.Build.props` и `tests/Directory.Build.props`. Каждый вложенный `Directory.Build.props` должен явно импортировать родительский до собственных настроек: MSBuild автоматически находит только ближайший файл.
- Допускай props-файл отдельного проекта, если настройки действительно специфичны для него; сохраняй цепочку импорта родительских файлов.
- Задавай `InternalsVisibleTo` со стороны production-проектов только для нужных тестовых сборок. Общие правила можно разместить в `src/Directory.Build.props`.
- Используй NUnit и NSubstitute для .NET-тестов. Общие `PackageReference` тестовых проектов, включая тестовый SDK и адаптер, выноси в `tests/Directory.Build.props`; не подключай их к production-проектам.
- Используй Testcontainers for .NET для контейнерных интеграционных тестов, прежде всего MinIO. Подключай пакет только нужным тестовым проектам, версию задавай через CPM. Изолируй тестовые данные, используй динамические порты, ожидание готовности и освобождение ресурсов; не обращайся к пользовательскому MinIO. SQLite проверяй на настоящей временной файловой БД с миграциями.
- Используй Central Package Management: `ManagePackageVersionsCentrally=true` и версии всех NuGet-пакетов через `PackageVersion` в корневом `Directory.Packages.props`. Не дублируй версии в `PackageReference` проектов или props-файлов.
- Зависимости React веди отдельно в `package.json` и lock-файле внутри `src/Ytdlp.Ui.Client/`.
- Поддерживай workflow в `.github/workflows/ci.yml`: job `build` выполняет сборку, тесты и проверку `dotnet publish`; job `docker` с `needs: build` собирает образ через Buildx и публикует его в GHCR.
- При push в основную ветку публикуй образ `ghcr.io/<repository-owner>/ytdlp-ui`; приводь имя к нижнему регистру. Для pull request выполняй проверки и сборку образа без входа в GHCR и без публикации.
- Используй для входа в GHCR `github.actor` и `GITHUB_TOKEN`. Выдавай `packages: write` только job публикации; для чтения репозитория используй `contents: read`.
- Формируй тег образа как `YYYY.M.D.<github.run_number>` по дате коммита в часовом поясе `Europe/Moscow`. Передавай теги и OCI labels через Docker metadata action.
- Не добавляй приватные NuGet feeds, секреты сборки и создание Git-тегов без отдельной необходимости. Автоматический деплой приложения в текущий pipeline не входит.

## Правила обработки загрузок

- Единственный пользовательский параметр задания — URL. Плейлисты и прямые эфиры отклоняются.
- Определяй дубликаты по нормализованному URL, без объединения разных ссылок по идентификатору ролика. При существующем задании отклоняй повторный URL, кроме случая удаленного готового файла: тогда ставь новую попытку старого задания, сохраняя его ID и историю. Ручной повтор использует тот же механизм. Одновременные запросы не должны создавать две активные попытки.
- Реализуй жизненный цикл задания как конечный автомат с явными событиями, переходами и проверками условий. Этапы являются состояниями: `Queued → Downloading → Preparing → Uploading → CleaningUp → Completed`; удаление результата — `Completed → Deleting → Deleted`. Предусмотри `Failed`, `Canceling`, `Canceled` и сохраняемую точку продолжения. Доступность опубликованного файла храни отдельно как факт о хранилище; изменения жизненного цикла проходят через общие правила автомата.
- Одновременно обрабатывается одно задание; остальные ожидают в сохраняемой очереди.
- Выбирай видео с аудио до 1080p с предпочтением MP4. Допускается другой исходный формат; перекодирование не входит в MVP.
- Последовательность этапов: скачивание, объединение дорожек при необходимости, отправка в S3, очистка локальных файлов после успешной отправки.
- Сохраняй состояние каждого этапа и каждой попытки в БД. Повтор создает новую попытку для той же загрузки и продолжает с проваленного этапа, используя готовые промежуточные результаты.
- Ставь `Completed` только после подтверждения публикации и локальной очистки. При ошибке очистки сохраняй доступность файла в S3, а повтор выполняй с `CleaningUp`. При ошибке удаления из S3 повтор продолжает `Deleting`; из `Deleted` повтор начинает скачивание заново. До повторного внешнего действия проверяй, не завершилось ли оно до сбоя; сохраняй намерение до начала действия.
- При ошибке сохраняй временные файлы до ручного повтора или отмены. Не добавляй автоматическое удаление по сроку.
- Отмена останавливает обработку и удаляет промежуточные результаты задания; история сохраняется. Очистка должна затрагивать только файлы этого задания.
- Запрещай отмену в `CleaningUp`, а также в `Failed` и `Queued` с `ResumeState=CleaningUp`. Исключай отмену из `allowedActions`, отклоняй команду на сервере с `409`; ошибка очистки допускает ее повтор. Проверяй запрет атомарно с переходом состояния, включая гонку отмены с завершением Uploading.
- Удаление готового файла сохраняет задание и историю; повтор после удаления начинает скачивание с начала. Подтверждай отсутствие объекта в S3: недоступность хранилища или отказ доступа не означают удаление. Публичный GET отсутствующего файла не должен создавать или повторять задания.
- После перезапуска помечай прерванную обработку ошибкой для ручного повтора. Ожидающие задания остаются в очереди.
- Не добавляй ограничения размера файла или длительности ролика в MVP.

## Библиотека и доступ

- Публичный каталог показывает все файлы bucket, включая добавленные вне приложения. SQLite не является источником состава библиотеки.
- Используй плоский список без навигации по папкам, с названием, размером, датой изменения и действием скачивания.
- Показывай каталог целиком, без пользовательской пагинации и кнопки «Показать еще». При чтении S3 обрабатывай все страницы ответа хранилища, чтобы вернуть полный список файлов.
- Передавай файлы посетителю потоком через бэкенд, без загрузки всего файла в память и без перенаправления на прямой URL MinIO.
- Создание заданий, просмотр их истории, повтор, отмена и удаление файлов требуют авторизации на сервере; скрытие элементов UI не заменяет проверку доступа.
- Форма входа открывается в правом верхнем углу. После входа та же страница библиотеки получает функции управления; отдельная административная страница в MVP не нужна.
- Храни JWT в `sessionStorage` в пределах сессии вкладки, сохраняя вход при перезагрузке страницы. После загрузки UI проверяй действительность токена через API; наличие токена в хранилище само по себе не подтверждает вход. Предусмотри кнопку выхода; после выхода или `401` текущей сессии очищай токен и административные данные из UI. Выход не должен отменять фоновые задания.
- Передавай JWT только через заголовок `Authorization: Bearer <token>`, без аутентификации через cookie или query-параметры. Проверяй подпись, разрешенный алгоритм, issuer, audience, срок действия и активность сессии; отзыв при выходе согласуй с техническим проектом. Не храни JWT в localStorage и не сохраняй пароль в браузерном хранилище.
- В MVP используется один администратор с учетными данными в конфигурации бэкенда. Учетные данные S3 и администратора не должны попадать во фронтенд или логи. В примерах конфигурации используй демонстрационные значения.
- Передавай URL в yt-dlp отдельным аргументом процесса, без конструирования shell-команды из пользовательского ввода.

## Интерфейс и локализация

- Ориентируй визуальный стиль на Google Material 3, Material You и Material 3 Expressive, со средней плотностью элементов и действиями справа внизу карточек.
- Поддерживай адаптивный интерфейс для телефона и десктопа, включая все административные действия.
- Выбирай светлую или темную тему по настройкам устройства, без ручного переключателя в MVP.
- Показывай блок «Загрузки» с очередью и историей над каталогом только авторизованному администратору. Не запрашивай и не передавай данные заданий анонимному посетителю.
- Открывай форму с URL по кнопке создания задания. Удаление готовых файлов добавляй в тот же каталог после входа администратора.
- В карточке задания показывай название или URL, текущий этап, прогресс, дату создания, ошибку при наличии и доступные действия. Если процент этапа неизвестен, используй индикатор без процента; не симулируй прогресс. Скорость и оставшееся время в MVP не нужны.
- Не добавляй поиск по файлам в MVP.
- Локализуй интерфейс через ресурсы для английского и русского языков. Выбирай язык по предпочтениям браузера; английский используй как базовый и запасной. Ручной переключатель языка не добавляй.
- Выноси пользовательские строки, включая валидацию и названия состояний, в ресурсы; форматируй даты и числа с учетом языка. Исходные сообщения yt-dlp и других инструментов допускаются без перевода в диагностических подробностях.

## Docker и конфигурация

- Поддерживай multi-stage сборку Docker-образа с необходимыми зависимостями приложения, yt-dlp и средствами объединения дорожек.
- Поддерживай полный функционал приложения на `linux/amd64` и `linux/arm64`. Собирай обе платформы через Buildx и публикуй в GHCR под одним тегом с общим manifest list.
- Выбирай базовые образы и runtime-зависимости для целевой архитектуры, включая .NET, нативные библиотеки SQLite, yt-dlp и FFmpeg. Не копируй в ARM64-образ исполняемые файлы или нативные библиотеки, собранные только для AMD64, и наоборот.
- В workflow указывай `platforms: linux/amd64,linux/arm64`; используй runners соответствующей архитектуры или QEMU для выполнения команд целевой платформы.
- Основной сценарий — отдельный контейнер приложения с подключением к уже существующему MinIO. Compose с MinIO служит вспомогательным вариантом для локального запуска.
- SQLite и временные файлы должны располагаться в сохраняемых volumes.
- Параметры MinIO, учетные данные и пути хранения задавай через конфигурацию с возможностью переопределения переменными окружения.
- Документируй фактические команды сборки и запуска, параметры конфигурации и подключаемые volumes.

## Проверка изменений

- Выполняй проверки, соответствующие изменению; не заявляй об успешной проверке, если она не запускалась.
- Запускай тесты с Testcontainers в CI с доступным Docker до публикации образа; отсутствие Docker не должно приводить к незаметному пропуску этих проверок. Поддерживай отдельный запуск unit-тестов без Docker. Если локально Docker недоступен, явно сообщай о невыполненных интеграционных тестах.
- При изменениях интеграции сборки проверяй `dotnet build` и `dotnet publish`, включая наличие собранного фронтенда в результате публикации.
- При изменениях контейнера проверяй сборку образа и запуск, если Docker доступен.
- Не запускай приложение и smoke-тесты Docker-образов в CI. Проверяй запуск на обеих архитектурах отдельно в подходящем окружении: API, React, SQLite, yt-dlp и FFmpeg. Если локальная проверка какой-либо платформы недоступна, явно указывай это; не считай сборку доказательством работоспособности.
- Для логики очереди и этапов проверяй сохранение очереди, повтор проваленного этапа, отмену с очисткой и восстановление после перезапуска.
- Для изменений доступа проверяй публичное чтение и запрет административных операций без входа.
- В итоговом сообщении кратко указывай, что изменено, что проверено и какие проверки остались невыполненными.

## За пределами MVP

Прямые эфиры, выбор формата, перекодирование и телеметрия скачивания отложены до отдельных итераций. Не реализуй их без нового запроса пользователя.
